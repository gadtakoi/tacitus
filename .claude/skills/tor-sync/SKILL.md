# ToR sync — актуализация технического задания

Полные правила: [.ai/project/tor-rules.md](../../../.ai/project/tor-rules.md). Ниже — рабочий порядок.

Единственный файл ТЗ: `docs/ToR_<Project>_v1.0.md`.
Он описывает сервис так, **как будто был написан до разработки и по нему сервис и создан**.
Не changelog, не отчет о работе — актуальное ТЗ на текущее состояние.

## Порядок

1. **Определи, затронуты ли требования.** Изменение требует правки ТЗ, если оно меняет:
   поведение и бизнес-правила; HTTP-контракты (endpoints, схемы, коды ошибок); роли и доступ;
   модель данных и миграции; фоновые процессы и ротацию архивов; интеграции; переменные окружения;
   состав сервисов и деплой; нефункциональные лимиты; пользовательские сценарии фронтенда.
   Рефакторинг без смены контрактов, тесты, форматирование — не требуют.

2. **Открой ТЗ.** Если файла нет — создай его по текущему состоянию кода и конфигурации,
   по структуре из `.ai/project/tor-rules.md` (15 фиксированных разделов + шапка с версией и датой).

3. **Внеси правку точечно.** Меняй только те разделы, которых касается изменение.
   Не переписывай файл целиком без необходимости — diff должен быть обозримым для review.

4. **Проверь по стилю ТЗ:**
   - формулировки «Сервис должен…», «Система обеспечивает…», настоящее время;
   - нет слов «добавлено», «теперь», «ранее», «в рамках задачи», ссылок на коммиты, PR, этапы, `plan/*`;
   - нет секретов, реальных паролей, токенов, ключей, внутренних IP и hostname — только имена
     переменных окружения и их назначение;
   - по ТЗ сервис воспроизводим с нуля без чтения исходников.

5. **Обнови дату актуализации** в шапке файла. Имя и версию файла не меняй.

6. **Включи правку ТЗ в тот же коммит**, что и изменение кода.

## Отчет

В итоговом ответе одной строкой: какие разделы ТЗ обновлены, либо почему ТЗ не затронуто.

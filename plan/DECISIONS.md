# Реестр архитектурных решений (ADR)

## ADR-001: Выбор языка программирования

**Дата:** 2026-06-03
**Статус:** Принято

### Контекст
Необходимо выбрать язык разработки для проекта Tacitus.

### Решение
Использовать Python версии 3.14 и выше.

### Обоснование
- Современная экосистема и богатая стандартная библиотека
- Простота разработки и читаемость кода
- Указано в `pyproject.toml`

### Последствия
- Ограничение на минимальную версию Python
- Доступ к современным возможностям языка

### Альтернативы
- TypeScript/Node.js — отклонено в пользу Python-экосистемы
- Go — отклонено из-за скорости разработки

## ADR-002: Выбор веб-фреймворка

**Дата:** 2026-06-03
**Статус:** Принято

### Контекст
Необходим ASGI-фреймворк для построения REST API.

### Решение
Использовать FastAPI.

### Обоснование
- Нативная поддержка Pydantic для валидации
- Автогенерация OpenAPI/Swagger
- Асинхронная архитектура на базе Starlette
- Широкая документация и сообщество

### Последствия
- Строгая типизация входных/выходных данных
- Простота интеграции зависимостей (Depends)

### Альтернативы
- Django — избыточен для MVP
- Flask — меньше встроенной валидации

## ADR-003: Выбор S3-хранилища

**Дата:** 2026-06-03
**Статус:** Принято

### Контекст
Приложению требуется объектное хранилище для файлов.

### Решение
Использовать MinIO в Docker Compose для локальной разработки.

### Обоснование
- Полная совместимость с S3 API (boto3)
- Лёгкий деплой через Docker
- Возможность миграции на AWS S3 / Yandex Cloud без изменения кода

### Последствия
- Требуется init-контейнер для создания bucket
- Console доступна только внутри сети (security)

### Альтернативы
- AWS S3 — требует cloud account для разработки
- LocalStack — избыточен, MinIO проще

## ADR-004: Выбор механизма авторизации

**Дата:** 2026-06-04
**Статус:** Принято

### Контекст
Необходима аутентификация пользователей и защита API endpoints.

### Решение
JWT access tokens (python-jose + passlib).

### Обоснование
- Stateless — не требует сессий на сервере
- Простая интеграция с FastAPI (Depends)
- Frontend легко хранит токен в localStorage

### Последствия
- Токен нельзя отозвать до истечения TTL (MVP-ограничение)
- Refresh tokens не реализованы в MVP

### Альтернативы
- OAuth2 + OpenID Connect — избыточен для MVP
- Session-based auth — требует хранилища сессий

## ADR-005: Выбор алгоритма хеширования паролей

**Дата:** 2026-06-04
**Статус:** Принято

### Контекст
Passlib с bcrypt вызывал `ValueError` и `AttributeError` при использовании bcrypt 5.0.

### Решение
Использовать `pbkdf2_sha256` через passlib.

### Обоснование
- Встроен в passlib, не требует сторонних бинарных зависимостей
- Устойчив к известным проблемам bcrypt 5.0
- Достаточно безопасен для MVP

### Последствия
- Алгоритм можно сменить на argon2 в будущем без потери совместимости (passlib unified API)

### Альтернативы
- bcrypt (<5.0) — требует пиннинга версии, возможны конфликты в будущем
- argon2 — требует дополнительных зависимостей (`argon2-cffi`)

## ADR-006: In-memory хранилище пользователей

**Дата:** 2026-06-04
**Статус:** Заменено ADR-010

### Контекст
Для MVP не требуется полноценная БД.

### Решение
In-memory dict `_users` в `auth_service.py`.

### Обоснование
- Минимальная сложность, нет миграций
- Достаточно для демонстрации и тестирования
- Легко заменить на SQLAlchemy + PostgreSQL позже

### Последствия
- Данные теряются при перезапуске приложения
- Нет масштабирования на несколько инстансов

### Альтернативы
- PostgreSQL + SQLAlchemy — требует миграций и дополнительного сервиса
- SQLite — проще, но всё равно требует Alembic для production

## ADR-010: Переход на PostgreSQL для хранения состояния приложения

**Дата:** 2026-06-13
**Статус:** Принято

### Контекст
In-memory хранилища (ADR-006) не подходят для production: данные теряются при
перезапуске, невозможно масштабировать приложение на несколько инстансов,
отсутствует персистентность security-событий и токенов.

### Решение
Перевести все процессные (in-memory) хранилища на PostgreSQL с использованием
SQLAlchemy 2.0 (asyncpg) и Alembic:

- `users` — учётные записи и хеши паролей.
- `refresh_tokens` — выпущенные refresh-токены (хранится SHA-256 хеш).
- `revoked_tokens` — чёрный список access-токенов по `jti`.
- `failed_login_attempts` — неудачные попытки входа для brute-force защиты.
- `security_events` — security-события и подозрительная активность.

Rate-limiting остаётся во внешнем хранилище (`memory://` для dev,
`redis://...` для production), так как библиотека `limits` не поддерживает
PostgreSQL в качестве storage URI.

### Обоснование
- Персистентность данных между перезапусками.
- Возможность горизонтального масштабирования (несколько инстансов app
  работают с одной БД).
- Целостность и атомарность через транзакции PostgreSQL.
- Уникальные ограничения и индексы на уровне БД.
- Alembic обеспечивает версионирование схемы.

### Последствия
- Появился слой репозиториев (`app/db/repositories/`).
- Все сервисы теперь принимают `AsyncSession`.
- Тесты требуют PostgreSQL (пропускаются автоматически при её отсутствии).
- Rate-limiting требует Redis в production.

### Альтернативы
- SQLite + aiosqlite — отклонено из-за несовместимости с PostgreSQL-специфичными
  конструкциями (`JSONB`, `ON CONFLICT DO NOTHING`) и меньшей готовности к
  production.
- Продолжать использовать in-memory хранилища — отклонено из-за ограничений
  масштабируемости и надёжности.

## ADR-008: Nginx reverse proxy

**Дата:** 2026-06-03
**Статус:** Принято

### Контекст
Нужен единый entrypoint для фронтенда и API.

### Решение
Nginx проксирует `/api/`, `/auth/`, `/files/` на FastAPI, а `/` отдаёт React SPA.

### Обоснование
- Единый порт `80` для всех запросов
- Терминация статики на Nginx (быстрее, чем через FastAPI)
- Security headers из коробки

### Последствия
- Nginx конфиг должен поддерживаться при добавлении новых routes

### Альтернативы
- Traefik — сложнее для локальной разработки
- Чисто FastAPI static files — медленнее

## ADR-009: Docker Compose для оркестрации

**Дата:** 2026-06-03
**Статус:** Принято

### Контекст
Необходимо поднимать несколько сервисов (app, nginx, minio) единой командой.

### Решение
Docker Compose v2 с фиксированными версиями образов.

### Обоснование
- Декларативное описание стека
- Простой локальный запуск (`docker compose up -d`)

- Требуется Docker Engine >= 24.x
- Для production может потребоваться Kubernetes

### Альтернативы
- Docker Swarm — избыточен для MVP
- Kubernetes — избыточен для MVP

## ADR-011: Модель аутентификации при скачивании файлов из S3/MinIO

**Дата:** 2026-06-13
**Статус:** Принято

### Контекст

Файлы хранятся в S3-совместимом хранилище (MinIO). Необходимо определить,
как аутентифицировать клиентов при скачивании файлов и как минимизировать
риски утечки прямых ссылок.

### Решение

Использовать двухэтапную схему:

1. **JWT Bearer token** защищает endpoint `GET /files/{filename}`. Токен
   проверяется подписью и сверяется с чёрным списком `revoked_tokens` в
   PostgreSQL (`get_current_user`).
2. **Presigned URL** выдаётся только после успешной аутентификации. Ссылка
   генерируется boto3 (`generate_presigned_url`) с ограниченным сроком жизни
   (default 300 секунд, настраивается через
   `TACITUS_PRESIGNED_URL_EXPIRATION`). Клиент скачивает файл напрямую из
   S3/MinIO по этой ссылке.

Дополнительные меры:

- Rate limit 30 запросов в минуту на пользователя на `GET /files/{filename}`.
- Security event `file.download` логируется при каждом запросе.
- Перед генерацией URL выполняется `head_object`, чтобы не выдавать ссылки на
  несуществующие файлы.

### Обоснование

- Presigned URL не требует от клиента S3 credentials — аутентификация
  концентрируется в одном JWT-защищённом endpoint.
- Подписанная ссылка криптографически непредсказуема и ограничена по времени,
  что снижает риск от утечки.
- Проверка существования объекта через `head_object` улучшает UX (чистый 404)
  и предотвращает генерацию бесполезных ссылок.

### Последствия

- Время жизни ссылки конфигурируется отдельно от TTL JWT access token.
- Необходимо следить за синхронизацией часов между сервером приложения и
  S3/MinIO, иначе presigned URL может истекать раньше/позже ожидаемого.
- Bucket policy должна оставаться закрытой для публичного доступа.

### Альтернативы

- Проксирование скачивания через FastAPI — отклонено: увеличивает нагрузку на
  приложение и лишает преимуществ прямого доступа к объектному хранилищу.
- Индивидуальные IAM credentials для каждого пользователя — отклонено:
  избыточно для MVP, усложняет управление ключами.

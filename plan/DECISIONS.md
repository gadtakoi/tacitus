## ADR-001: Выбор языка программирования

**Дата:** 2026-06-03
**Статус:** Принято

### Контекст
Необходимо выбрать язык разработки для проекта Tacitus.

### Решение
Использовать Python версии 3.14 и выше.

### Обоснование
- Современная экосистема и богатая стандартная библиотека

### Альтернативы

## ADR-005: Выбор алгоритма хеширования паролей

**Дата:** 2026-06-04
**Статус:** Принято

### Контекст
Passlib с bcrypt вызывал `ValueError` и `AttributeError` при использовании bcrypt 5.0.

### Решение
Использовать `pbkdf2_sha256` через passlib.

### Обоснование
- Встроен в passlib, не требует сторонних бинарных зависимостей
- Устойчив к известным проблемам bcrypt 5.0
- Достаточно безопасен для MVP

### Последствия
- Алгоритм можно сменить на argon2 в будущем без потери совместимости (passlib unified API)

### Альтернативы
- bcrypt (<5.0) — требует пиннинга версии, возможны конфликты в будущем
- argon2 — требует дополнительных зависимостей (`argon2-cffi`)

## ADR-010: Переход на PostgreSQL для хранения состояния приложения

**Дата:** 2026-06-13
**Статус:** Принято

### Контекст
In-memory хранилища (ADR-006) не подходят для production: данные теряются при
перезапуске, невозможно масштабировать приложение на несколько инстансов,
отсутствует персистентность security-событий и токенов.

### Решение
Перевести все процессные (in-memory) хранилища на PostgreSQL с использованием
SQLAlchemy 2.0 (asyncpg) и Alembic:

- `users` — учётные записи и хеши паролей.
- `refresh_tokens` — выпущенные refresh-токены (хранится SHA-256 хеш).
- `revoked_tokens` — чёрный список access-токенов по `jti`.
- `failed_login_attempts` — неудачные попытки входа для brute-force защиты.
- `security_events` — security-события и подозрительная активность.

Rate-limiting остаётся во внешнем хранилище (`memory://` для dev,
`redis://...` для production), так как библиотека `limits` не поддерживает
PostgreSQL в качестве storage URI.

### Обоснование
- Персистентность данных между перезапусками.
- Возможность горизонтального масштабирования (несколько инстансов app
  работают с одной БД).
- Целостность и атомарность через транзакции PostgreSQL.
- Уникальные ограничения и индексы на уровне БД.
- Alembic обеспечивает версионирование схемы.

### Последствия
- Появился слой репозиториев (`app/db/repositories/`).
- Все сервисы теперь принимают `AsyncSession`.
- Тесты требуют PostgreSQL (пропускаются автоматически при её отсутствии).
- Rate-limiting требует Redis в production.

### Альтернативы
- SQLite + aiosqlite — отклонено из-за несовместимости с PostgreSQL-специфичными
  конструкциями (`JSONB`, `ON CONFLICT DO NOTHING`) и меньшей готовности к
  production.
- Продолжать использовать in-memory хранилища — отклонено из-за ограничений
  масштабируемости и надёжности.

## ADR-011: Модель аутентификации при скачивании файлов из S3/MinIO

**Дата:** 2026-06-13
**Статус:** Принято

### Контекст

Файлы хранятся в S3-совместимом хранилище (MinIO). Необходимо определить,
как аутентифицировать клиентов при скачивании файлов и как минимизировать
риски утечки прямых ссылок.

### Решение

Использовать двухэтапную схему:

1. **JWT Bearer token** защищает endpoint `GET /files/{filename}`. Токен
   проверяется подписью и сверяется с чёрным списком `revoked_tokens` в
   PostgreSQL (`get_current_user`).
2. **Presigned URL** выдаётся только после успешной аутентификации. Ссылка
   генерируется boto3 (`generate_presigned_url`) с ограниченным сроком жизни
   (default 300 секунд, настраивается через
   `TACITUS_PRESIGNED_URL_EXPIRATION`). Клиент скачивает файл напрямую из
   S3/MinIO по этой ссылке.

Дополнительные меры:

- Rate limit 30 запросов в минуту на пользователя на `GET /files/{filename}`.
- Security event `file.download` логируется при каждом запросе.
- Перед генерацией URL выполняется `head_object`, чтобы не выдавать ссылки на
  несуществующие файлы.

### Обоснование

- Presigned URL не требует от клиента S3 credentials — аутентификация
  концентрируется в одном JWT-защищённом endpoint.
- Подписанная ссылка криптографически непредсказуема и ограничена по времени,
  что снижает риск от утечки.
- Проверка существования объекта через `head_object` улучшает UX (чистый 404)
  и предотвращает генерацию бесполезных ссылок.

### Последствия

- Время жизни ссылки конфигурируется отдельно от TTL JWT access token.
- Необходимо следить за синхронизацией часов между сервером приложения и
  S3/MinIO, иначе presigned URL может истекать раньше/позже ожидаемого.
- Bucket policy должна оставаться закрытой для публичного доступа.

### Альтернативы

- Проксирование скачивания через FastAPI — отклонено: увеличивает нагрузку на
  приложение и лишает преимуществ прямого доступа к объектному хранилищу.
- Индивидуальные IAM credentials для каждого пользователя — отклонено:
  избыточно для MVP, усложняет управление ключами.

## ADR-012: Модель аутентификации MediaMTX (RTSP и Control API)

**Дата:** 2026-09-03
**Статус:** Принято

### Контекст

MediaMTX поставляется с анонимным дефолтом. Если секция `authInternalUsers`
не объявлена, встроенный список выдаёт `user: any` с пустым паролем права
`publish`, `read` и `playback` на **все** пути. Аудит 2026-09-03 показал, что
проект этот дефолт не переопределял, при этом порт `8554` публиковался на
`0.0.0.0`, а `record: yes` включена. Практически это означало: любой, кто
достаёт до порта, публикует поток в `cam1`/`live`, читает чужие потоки, а
запись уходит на диск и далее в S3.

Вторая половина того же дефолта выдаёт action `api` только адресам
`127.0.0.1/32` и `::1/128`. Бэкенд обращается к Control API по сети Docker,
поэтому `GET /streams` в реально запущенном стеке отвечал 502 (MediaMTX
возвращал 401). Ни один тест этого не ловил — исходящий запрос не проверялся.

### Решение

Использовать встроенную аутентификацию MediaMTX (`authMethod: internal`) с
явным списком учётных записей, разделённым по действиям:

| Учётная запись | Действия | Назначение |
|---|---|---|
| `publisher` | `publish` | Камеры и другие источники |
| `reader` | `read`, `playback` | Потребители потоков и записей |
| `tacitus-api` | `api` | Бэкенд Tacitus для `GET /streams` |

Дополнительные меры:

- Бэкенд ходит в Control API с HTTP Basic (`TACITUS_MTX_API_USER` /
  `TACITUS_MTX_API_PASSWORD`); отказ по 401/403 логируется отдельно и
  превращается в 502 с явным `MediaMTX API authentication failed`.
- Порт RTSP публикуется на loopback по умолчанию
  (`TACITUS_MTX_RTSP_BIND=127.0.0.1`); выход в сеть — осознанное действие
  оператора.
- Production-конфиг рендерится Ansible из переменных, пригодных для vault;
  `validate_startup_settings()` и pre-check в `ansible/playbook.yml`
  отказываются работать с dev-паролями.

### Обоснование

- Разделение по действиям ограничивает ущерб от утечки одного пароля: пароль
  камеры не даёт ни чтения архива, ни доступа к Control API.
- Внутренний механизм MediaMTX не требует новых компонентов — это минимальное
  безопасное изменение по сравнению с внешним auth-сервисом.
- Явный список полностью вытесняет анонимный дефолт: это проверено
  эмпирически на MediaMTX 1.15.1 (анонимные publish, read и api получают 401).

### Последствия

- **Credentials обязаны лежать в самом YAML-файле.** Переменные окружения
  `MTX_AUTHINTERNALUSERS_<n>_PASS` не переопределяют запись `<n>` из файла, а
  дописывают новую — проверено на 1.15.1. Поэтому production-файл
  генерируется Ansible, а не патчится через env.
- RTSP использует Basic-аутентификацию поверх нешифрованного транспорта
  (`rtspEncryption: no`), то есть пароль передаётся по сети в открытом виде.
  Порт обязан быть закрыт для недоверенных сетей; при выходе за периметр
  требуется RTSPS или VPN.
- Существующие публикующие клиенты должны быть обновлены: URL становится
  `rtsp://<publisher>:<password>@host:8554/<path>`.
- Дефолт bind на loopback меняет поведение: камере в локальной сети нужно
  явно задать `TACITUS_MTX_RTSP_BIND=0.0.0.0` вместе с правилом firewall.

### Альтернативы

- `authMethod: http` с делегированием в Tacitus — отклонено на этом шаге:
  требует нового endpoint, хранения учётных данных потоков и заметно большего
  объёма изменений. Остаётся кандидатом, если понадобятся права на уровне
  отдельных путей и ротация без перезапуска.
- Ограничение только на уровне firewall без аутентификации — отклонено:
  единственный барьер, отказ которого сразу открывает публикацию и чтение.
- Один общий аккаунт на все действия — отклонено: утечка пароля камеры
  открывала бы и архив, и Control API.

## ADR-013: Отказ от хранения per-path credentials потоков в БД

**Дата:** 2026-09-03
**Статус:** Принято

### Контекст

Таблица `streams` и схема `StreamCredentials` содержали поля `publish_user`,
`publish_pass`, `read_user`, `read_pass` — задел под CRUD потоков из
`PLAN_stage_8_mediamtx.md` §3.1.3, где планировалась «поддержка параметров в
`mediamtx.yml`: `publishUser`, `publishPass`, `readUser`, `readPass`».

Проверка схемы параметров пути у запущенного MediaMTX 1.15.1
(`GET /v3/config/pathdefaults/get`) показала: из 82 параметров ни одного,
относящегося к аутентификации, кроме `srtReadPassphrase` и
`srtPublishPassphrase` (SRT в проекте отключён). Per-path поля
`publishUser`/`publishPass`/`readUser`/`readPass` из MediaMTX убраны в пользу
глобального списка `authInternalUsers`, где ограничение по пути задаётся через
`permissions[].path` (см. ADR-012).

Таким образом колонки хранили пароли в открытом виде под API, которого не
существует, и ни один компонент их не читал: роутеров, подключённых к слою
конфигурации потоков, нет.

### Решение

Удалить credentials из модели данных и из транспортных схем:

- миграция `b2d8f6a3c714` удаляет четыре колонки из `streams`;
- `StreamCredentials` удалена; поле `credentials` убрано из `StreamConfig`,
  `StreamCreateRequest` и `StreamUpdateRequest`;
- задел под CRUD (`stream_config_service.py`, `db/repositories/streams.py`,
  таблица `streams`) сохранён — он остаётся основанием для
  `PLAN_stage_8_mediamtx.md` §3.1.2.

Аутентификация потоков полностью определяется `authInternalUsers` (ADR-012).

### Обоснование

- Устраняется хранение plaintext-паролей, не имеющее потребителя, — прямое
  требование `.ai/system/security-rules.md`.
- Схема данных перестаёт описывать несуществующий контракт MediaMTX, что
  иначе вводило бы в заблуждение при доработке CRUD.
- Изменение минимально: удаляются только поля, а не работающая структура.

### Последствия

- `PLAN_stage_8_mediamtx.md` §3.1.3 в части per-path credentials более
  неисполним как написан и требует переработки под `authInternalUsers`.
- При будущей реализации CRUD потоков управление доступом придётся
  проектировать отдельно — либо через генерацию `authInternalUsers`, либо
  через `authMethod: http` (отложено в ADR-012).
- `downgrade` возвращает колонки, но не значения: данные удаляются вместе со
  столбцами. На момент миграции таблица не использовалась приложением.

### Альтернативы

- Удалить весь слой конфигурации потоков целиком — отклонено: это отменило бы
  запланированную функциональность `PLAN_stage_8_mediamtx.md` §3.1.2, а
  решение о судьбе плана выходит за рамки устранения дефекта.
- Хешировать пароли вместо удаления — отклонено: MediaMTX всё равно не может
  их прочитать, а хеш не решает задачу аутентификации потока.

## ADR-014: Имитатор RTSP-потока на образе MediaMTX за профилем compose

**Дата:** 2026-09-06
**Статус:** Принято

### Контекст

Конвейер приёма видео — публикация → путь MediaMTX → `GET /streams` → запись
на диск → архив в S3 — никогда не проверялся автоматически. Для проверки
требовался либо настоящий источник, либо команда `ffmpeg`, существовавшая
только как пример в тексте планов (`PLAN_stage_7_mediamtx.md:178`). Из-за
этого `docs/E2E_CHECKLIST.md` §6 описывал проверку словами, а `pytest tests/`
не поднимал ни одного потока: `test_streams_router.py` работает с
замоканным MediaMTX.

Нужен воспроизводимый источник тестового видео. Ключевое ограничение: он
держит действующие учётные данные публикатора и наполняет `recordings/`, то
есть на сервере его быть не должно ни при каких обстоятельствах.

### Решение

1. **Имитатор — сервис `stream-simulator` в `docker-compose.yml` за профилем
   `simulator`**, а не скрипт с `ffmpeg` на хосте. Профиль — первый в этом
   файле. Управление — через `scripts/simulate-stream.sh`.
2. **Сервис работает на образе `bluenviron/mediamtx:1.15.1-ffmpeg`** — том же,
   что и сам MediaMTX, с переопределённым `entrypoint`.
3. **Точка входа — POSIX `sh`** (`scripts/simulate-stream-entrypoint.sh`).
4. **Пароль публикатора приходит только из окружения**, без fallback в
   compose: `${TACITUS_SIM_PUBLISH_PASSWORD:-}`.
5. **Сквозная проверка — отдельный скрипт** `scripts/e2e-stream-check.sh`, а
   не модуль pytest и не расширение `scripts/healthcheck.sh`.

### Обоснование

- Сервис в compose ходит на `mediamtx:8554` по `tacitus-network`, поэтому не
  зависит от `TACITUS_MTX_RTSP_BIND=127.0.0.1` и не требует ffmpeg на хосте
  разработчика (рабочая машина — Windows).
- Образ MediaMTX уже несёт ffmpeg 6.1.2 с libx264 и lavfi, уже закреплён
  точным тегом и уже покрыт `test_compose_pinning.py`. Отдельный
  `jrottenberg/ffmpeg` добавил бы запись в цепочку поставок и вторую версию
  ffmpeg, расходящуюся с той, что использует сам сервер.
- В образе нет ни bash, ни python — только busybox ash, а установка
  зависимостей в рантайме запрещена (`test_compose_pinning.py`). POSIX `sh` —
  не стилистический выбор, а единственный доступный.
- Отсутствие fallback у пароля даёт второй барьер, независимый от профиля:
  на хосте, чей `.env` не определяет переменную, имитатор не может
  опубликовать поток вообще. Ansible к тому же вызывает compose без
  `--profile`, а `ansible/roles/app_deploy/templates/.env.j2` пароля
  публикатора не содержит.
- `scripts/healthcheck.sh` документирован как «только читает состояние» и
  направляется на production; публикация потока — мутация. Модуль pytest,
  пропускающийся без Docker, усугубил бы проблему молчаливых пропусков,
  описанную в `docs/testing.md`, а таймингам RTSP внутри pytest свойственна
  нестабильность. Статические гарантии вынесены в `tests/test_stream_simulator.py`,
  который выполняется всегда и без Docker.

### Последствия

- **Пароль неизбежно присутствует в argv ffmpeg внутри контейнера.**
  RTSP-мультиплексор ffmpeg не умеет передавать Basic-креденшелы вне URL
  (`-headers` работает только для HTTP). Митигации: пароль только в
  переменной окружения, никогда в `docker-compose.yml` и никогда в argv
  скрипта-обёртки; в лог уходит URL с заменой пароля на `***`; уровень логов
  ffmpeg зафиксирован на `error` (на `verbose` ffmpeg печатает URL целиком) и
  это закреплено тестом. Остаточная экспозиция — `ps` внутри контейнера и
  `docker inspect`.
- **Публиковать можно только в пути, описанные в `mediamtx.yml`.** Catch-all
  пути нет: публикация в необъявленный путь отвергается с `400 Bad Request`.
  В dev объявлены `cam1` и `live`, в production — только `cam1`, поэтому
  многопоточный сценарий возможен лишь локально. Обёртка проверяет список
  путей заранее и перечисляет доступные.
- **Непрерывная публикация наполняет `recordings/`** со скоростью ≈ 11 МБ/мин
  на поток при битрейте 1500k. Обёртка печатает оценку при старте, сквозная
  проверка использует облегчённый источник (640x480@15, 500k) и снимает
  имитатор через `trap EXIT`.
- Профиль становится новым механизмом гейтинга, чей отказ означает поставку
  фальш-камеры в production. Поэтому он закреплён сразу тремя способами:
  `test_simulator_is_profile_gated`, `test_production_deploy_does_not_enable_the_profile`
  и проверка в `scripts/healthcheck.sh`, считающая наличие контейнера на
  сервере ошибкой.
- Появляется неявная связка с ffmpeg-сборкой MediaMTX: обновление тега образа
  меняет и сервер, и клиента одновременно. Это считается приемлемым — версии
  и так обязаны быть согласованы, а `test_simulator_shares_the_mediamtx_image`
  не даёт им разойтись.

### Альтернативы

- **`ffmpeg` на хосте через `scripts/simulate-stream.sh`** — отклонено как
  единственный механизм: требует установленного ffmpeg (на Windows его обычно
  нет) и упирается в `TACITUS_MTX_RTSP_BIND=127.0.0.1`, из-за чего работает
  только на машине деплоя. Скрипт сохранён, но как обёртка над сервисом.
- **Отдельный образ `jrottenberg/ffmpeg` или `linuxserver/ffmpeg`** —
  отклонено: новая запись в цепочке поставок и второй ffmpeg, расходящийся с
  тем, что использует MediaMTX, ради возможности, которая уже есть.
- **Несколько реплик через `--scale`** — отклонено: несовместимо с
  `container_name`, который задают все остальные сервисы. Несколько потоков
  делаются перечислением путей в `TACITUS_SIM_PATHS`.
- **Постоянный сервис для негативного сценария** — отклонено: проверка
  «MediaMTX обязан отказать» одноразовая по смыслу, поэтому выполняется через
  `docker compose run --rm`.
- **Пробный файл-фикстура вместо `testsrc2`** — отклонено: потребовал бы
  бинарного артефакта в git ради экономии CPU, которой при 640x480@15 нет.

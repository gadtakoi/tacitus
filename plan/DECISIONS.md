## ADR-001: Выбор языка программирования

**Дата:** 2026-06-03 **Статус:** Принято

### Контекст

Необходимо выбрать язык разработки для проекта Tacitus.

### Решение

Использовать Python версии 3.14 и выше.

### Обоснование

- Современная экосистема и богатая стандартная библиотека
- Простота разработки и читаемость кода

### Последствия

- Ограничение на минимальную версию Python
- Доступ к современным возможностям языка

### Альтернативы

- TypeScript/Node.js — отклонено в пользу Python-экосистемы
- Go — отклонено из-за скорости разработки

## ADR-005: Выбор алгоритма хеширования паролей

**Дата:** 2026-06-04 **Статус:** Принято

### Контекст

Passlib с bcrypt вызывал `ValueError` и `AttributeError` при использовании bcrypt 5.0.

### Решение

Использовать `pbkdf2_sha256` через passlib.

### Обоснование

- Встроен в passlib, не требует сторонних бинарных зависимостей
- Устойчив к известным проблемам bcrypt 5.0
- Достаточно безопасен для MVP

### Последствия

- Алгоритм можно сменить на argon2 в будущем без потери совместимости (passlib unified API)

### Альтернативы

- bcrypt (<5.0) — требует пиннинга версии, возможны конфликты в будущем
- argon2 — требует дополнительных зависимостей (`argon2-cffi`)

## ADR-006: In-memory хранилище пользователей

**Дата:** 2026-06-04 **Статус:** Заменено ADR-010

Для MVP не требуется полноценная БД.

## ADR-010: Переход на PostgreSQL для хранения состояния приложения

**Дата:** 2026-06-13 **Статус:** Принято

### Контекст

In-memory хранилища (ADR-006) не подходят для production: данные теряются при перезапуске, невозможно масштабировать
приложение на несколько инстансов, отсутствует персистентность security-событий и токенов.

### Решение

Перевести все процессные (in-memory) хранилища на PostgreSQL с использованием SQLAlchemy 2.0 (asyncpg) и Alembic:

- `users` — учётные записи и хеши паролей.
- `refresh_tokens` — выпущенные refresh-токены (хранится SHA-256 хеш).
- `revoked_tokens` — чёрный список access-токенов по `jti`.
- `failed_login_attempts` — неудачные попытки входа для brute-force защиты.
- `security_events` — security-события и подозрительная активность.

Rate-limiting остаётся во внешнем хранилище (`memory://` для dev,
`redis://...` для production), так как библиотека `limits` не поддерживает PostgreSQL в качестве storage URI.

### Обоснование

- Персистентность данных между перезапусками.
- Возможность горизонтального масштабирования (несколько инстансов app работают с одной БД).
- Целостность и атомарность через транзакции PostgreSQL.
- Уникальные ограничения и индексы на уровне БД.
- Alembic обеспечивает версионирование схемы.

### Последствия

- Появился слой репозиториев (`app/db/repositories/`).
- Все сервисы теперь принимают `AsyncSession`.
- Тесты требуют PostgreSQL (пропускаются автоматически при её отсутствии).
- Rate-limiting требует Redis в production.

### Альтернативы

- SQLite + aiosqlite — отклонено из-за несовместимости с PostgreSQL-специфичными конструкциями (`JSONB`,
  `ON CONFLICT DO NOTHING`) и меньшей готовности к production.
- Продолжать использовать in-memory хранилища — отклонено из-за ограничений масштабируемости и надёжности.

## ADR-011: Модель аутентификации при скачивании файлов из S3/MinIO

**Дата:** 2026-06-13 **Статус:** Принято

### Контекст

Файлы хранятся в S3-совместимом хранилище (MinIO). Необходимо определить, как аутентифицировать клиентов при скачивании
файлов и как минимизировать риски утечки прямых ссылок.

### Решение

Использовать двухэтапную схему:

1. **JWT Bearer token** защищает endpoint `GET /files/{filename}`. Токен проверяется подписью и сверяется с чёрным
   списком `revoked_tokens` в PostgreSQL (`get_current_user`).
2. **Presigned URL** выдаётся только после успешной аутентификации. Ссылка генерируется boto3 (`generate_presigned_url`)
   с ограниченным сроком жизни (default 300 секунд, настраивается через
   `TACITUS_PRESIGNED_URL_EXPIRATION`). Клиент скачивает файл напрямую из S3/MinIO по этой ссылке.

Дополнительные меры:

- Rate limit 30 запросов в минуту на пользователя на `GET /files/{filename}`.
- Security event `file.download` логируется при каждом запросе.
- Перед генерацией URL выполняется `head_object`, чтобы не выдавать ссылки на несуществующие файлы.

### Обоснование

- Presigned URL не требует от клиента S3 credentials — аутентификация концентрируется в одном JWT-защищённом endpoint.
- Подписанная ссылка криптографически непредсказуема и ограничена по времени, что снижает риск от утечки.
- Проверка существования объекта через `head_object` улучшает UX (чистый 404)
  и предотвращает генерацию бесполезных ссылок.

### Последствия

- Время жизни ссылки конфигурируется отдельно от TTL JWT access token.
- Необходимо следить за синхронизацией часов между сервером приложения и S3/MinIO, иначе presigned URL может истекать
  раньше/позже ожидаемого.
- Bucket policy должна оставаться закрытой для публичного доступа.

### Альтернативы

- Проксирование скачивания через FastAPI — отклонено: увеличивает нагрузку на приложение и лишает преимуществ прямого
  доступа к объектному хранилищу.
- Индивидуальные IAM credentials для каждого пользователя — отклонено:
  избыточно для MVP, усложняет управление ключами.

## ADR-012: Модель аутентификации MediaMTX (RTSP и Control API)

**Дата:** 2026-09-03 **Статус:** Принято

### Контекст

MediaMTX поставляется с анонимным дефолтом. Если секция `authInternalUsers`
не объявлена, встроенный список выдаёт `user: any` с пустым паролем права
`publish`, `read` и `playback` на **все** пути. Аудит 2026-09-03 показал, что проект этот дефолт не переопределял, при
этом порт `8554` публиковался на
`0.0.0.0`, а `record: yes` включена. Практически это означало: любой, кто достаёт до порта, публикует поток в `cam1`/
`live`, читает чужие потоки, а запись уходит на диск и далее в S3.

Вторая половина того же дефолта выдаёт action `api` только адресам
`127.0.0.1/32` и `::1/128`. Бэкенд обращается к Control API по сети Docker, поэтому `GET /streams` в реально запущенном
стеке отвечал 502 (MediaMTX возвращал 401). Ни один тест этого не ловил — исходящий запрос не проверялся.

### Решение

Использовать встроенную аутентификацию MediaMTX (`authMethod: internal`) с явным списком учётных записей, разделённым по
действиям:

| Учётная запись | Действия           | Назначение                        |
|----------------|--------------------|-----------------------------------|
| `publisher`    | `publish`          | Камеры и другие источники         |
| `reader`       | `read`, `playback` | Потребители потоков и записей     |
| `tacitus-api`  | `api`              | Бэкенд Tacitus для `GET /streams` |

Дополнительные меры:

- Бэкенд ходит в Control API с HTTP Basic (`TACITUS_MTX_API_USER` /
  `TACITUS_MTX_API_PASSWORD`); отказ по 401/403 логируется отдельно и превращается в 502 с явным
  `MediaMTX API authentication failed`.
- Порт RTSP публикуется на loopback по умолчанию (`TACITUS_MTX_RTSP_BIND=127.0.0.1`); выход в сеть — осознанное действие
  оператора.
- Production-конфиг рендерится Ansible из переменных, пригодных для vault;
  `validate_startup_settings()` и pre-check в `ansible/playbook.yml`
  отказываются работать с dev-паролями.

### Обоснование

- Разделение по действиям ограничивает ущерб от утечки одного пароля: пароль камеры не даёт ни чтения архива, ни доступа
  к Control API.
- Внутренний механизм MediaMTX не требует новых компонентов — это минимальное безопасное изменение по сравнению с
  внешним auth-сервисом.
- Явный список полностью вытесняет анонимный дефолт: это проверено эмпирически на MediaMTX 1.15.1 (анонимные publish,
  read и api получают 401).

### Последствия

- **Credentials обязаны лежать в самом YAML-файле.** Переменные окружения
  `MTX_AUTHINTERNALUSERS_<n>_PASS` не переопределяют запись `<n>` из файла, а дописывают новую — проверено на 1.15.1.
  Поэтому production-файл генерируется Ansible, а не патчится через env.
- RTSP использует Basic-аутентификацию поверх нешифрованного транспорта (`rtspEncryption: no`), то есть пароль
  передаётся по сети в открытом виде. Порт обязан быть закрыт для недоверенных сетей; при выходе за периметр требуется
  RTSPS или VPN.
- Существующие публикующие клиенты должны быть обновлены: URL становится
  `rtsp://<publisher>:<password>@host:8554/<path>`.
- Дефолт bind на loopback меняет поведение: камере в локальной сети нужно явно задать `TACITUS_MTX_RTSP_BIND=0.0.0.0`
  вместе с правилом firewall.

### Альтернативы

- `authMethod: http` с делегированием в Tacitus — отклонено на этом шаге:
  требует нового endpoint, хранения учётных данных потоков и заметно большего объёма изменений. Остаётся кандидатом,
  если понадобятся права на уровне отдельных путей и ротация без перезапуска.
- Ограничение только на уровне firewall без аутентификации — отклонено:
  единственный барьер, отказ которого сразу открывает публикацию и чтение.
- Один общий аккаунт на все действия — отклонено: утечка пароля камеры открывала бы и архив, и Control API.

## ADR-013: Отказ от хранения per-path credentials потоков в БД

**Дата:** 2026-09-03 **Статус:** Принято

### Контекст

Таблица `streams` и схема `StreamCredentials` содержали поля `publish_user`,
`publish_pass`, `read_user`, `read_pass` — задел под CRUD потоков из
`PLAN_stage_8_mediamtx.md` §3.1.3, где планировалась «поддержка параметров в
`mediamtx.yml`: `publishUser`, `publishPass`, `readUser`, `readPass`».

Проверка схемы параметров пути у запущенного MediaMTX 1.15.1 (`GET /v3/config/pathdefaults/get`) показала: из 82
параметров ни одного, относящегося к аутентификации, кроме `srtReadPassphrase` и
`srtPublishPassphrase` (SRT в проекте отключён). Per-path поля
`publishUser`/`publishPass`/`readUser`/`readPass` из MediaMTX убраны в пользу глобального списка `authInternalUsers`,
где ограничение по пути задаётся через
`permissions[].path` (см. ADR-012).

Таким образом колонки хранили пароли в открытом виде под API, которого не существует, и ни один компонент их не читал:
роутеров, подключённых к слою конфигурации потоков, нет.

### Решение

Удалить credentials из модели данных и из транспортных схем:

- миграция `b2d8f6a3c714` удаляет четыре колонки из `streams`;
- `StreamCredentials` удалена; поле `credentials` убрано из `StreamConfig`,
  `StreamCreateRequest` и `StreamUpdateRequest`;
- задел под CRUD (`stream_config_service.py`, `db/repositories/streams.py`, таблица `streams`) сохранён — он остаётся
  основанием для
  `PLAN_stage_8_mediamtx.md` §3.1.2.

Аутентификация потоков полностью определяется `authInternalUsers` (ADR-012).

### Обоснование

- Устраняется хранение plaintext-паролей, не имеющее потребителя, — прямое требование `.ai/system/security-rules.md`.
- Схема данных перестаёт описывать несуществующий контракт MediaMTX, что иначе вводило бы в заблуждение при доработке
  CRUD.
- Изменение минимально: удаляются только поля, а не работающая структура.

### Последствия

- `PLAN_stage_8_mediamtx.md` §3.1.3 в части per-path credentials более неисполним как написан и требует переработки под
  `authInternalUsers`.
- При будущей реализации CRUD потоков управление доступом придётся проектировать отдельно — либо через генерацию
  `authInternalUsers`, либо через `authMethod: http` (отложено в ADR-012).
- `downgrade` возвращает колонки, но не значения: данные удаляются вместе со столбцами. На момент миграции таблица не
  использовалась приложением.

### Альтернативы

- Удалить весь слой конфигурации потоков целиком — отклонено: это отменило бы запланированную функциональность
  `PLAN_stage_8_mediamtx.md` §3.1.2, а решение о судьбе плана выходит за рамки устранения дефекта.
- Хешировать пароли вместо удаления — отклонено: MediaMTX всё равно не может их прочитать, а хеш не решает задачу
  аутентификации потока.

## ADR-014: Имитатор RTSP-потока на образе MediaMTX за профилем compose

**Дата:** 2026-09-06 **Статус:** Принято

### Контекст

Конвейер приёма видео — публикация → путь MediaMTX → `GET /streams` → запись на диск → архив в S3 — никогда не
проверялся автоматически. Для проверки требовался либо настоящий источник, либо команда `ffmpeg`, существовавшая только
как пример в тексте планов (`PLAN_stage_7_mediamtx.md:178`). Из-за этого `docs/E2E_CHECKLIST.md` §6 описывал проверку
словами, а `pytest tests/`
не поднимал ни одного потока: `test_streams_router.py` работает с замоканным MediaMTX.

Нужен воспроизводимый источник тестового видео. Ключевое ограничение: он держит действующие учётные данные публикатора и
наполняет `recordings/`, то есть на сервере его быть не должно ни при каких обстоятельствах.

### Решение

1. **Имитатор — сервис `stream-simulator` в `docker-compose.yml` за профилем
   `simulator`**, а не скрипт с `ffmpeg` на хосте. Профиль — первый в этом файле. Управление — через
   `scripts/simulate-stream.sh`.
2. **Сервис работает на образе `bluenviron/mediamtx:1.15.1-ffmpeg`** — том же, что и сам MediaMTX, с переопределённым
   `entrypoint`.
3. **Точка входа — POSIX `sh`** (`scripts/simulate-stream-entrypoint.sh`).
4. **Пароль публикатора приходит только из окружения**, без fallback в compose: `${TACITUS_SIM_PUBLISH_PASSWORD:-}`.
5. **Сквозная проверка — отдельный скрипт** `scripts/e2e-stream-check.sh`, а не модуль pytest и не расширение
   `scripts/healthcheck.sh`.

### Обоснование

- Сервис в compose ходит на `mediamtx:8554` по `tacitus-network`, поэтому не зависит от
  `TACITUS_MTX_RTSP_BIND=127.0.0.1` и не требует ffmpeg на хосте разработчика (рабочая машина — Windows).
- Образ MediaMTX уже несёт ffmpeg 6.1.2 с libx264 и lavfi, уже закреплён точным тегом и уже покрыт
  `test_compose_pinning.py`. Отдельный
  `jrottenberg/ffmpeg` добавил бы запись в цепочку поставок и вторую версию ffmpeg, расходящуюся с той, что использует
  сам сервер.
- В образе нет ни bash, ни python — только busybox ash, а установка зависимостей в рантайме запрещена
  (`test_compose_pinning.py`). POSIX `sh` — не стилистический выбор, а единственный доступный.
- Отсутствие fallback у пароля даёт второй барьер, независимый от профиля:
  на хосте, чей `.env` не определяет переменную, имитатор не может опубликовать поток вообще. Ansible к тому же вызывает
  compose без
  `--profile`, а `ansible/roles/app_deploy/templates/.env.j2` пароля публикатора не содержит.
- `scripts/healthcheck.sh` документирован как «только читает состояние» и направляется на production; публикация
  потока — мутация. Модуль pytest, пропускающийся без Docker, усугубил бы проблему молчаливых пропусков, описанную в
  `docs/testing.md`, а таймингам RTSP внутри pytest свойственна нестабильность. Статические гарантии вынесены в
  `tests/test_stream_simulator.py`, который выполняется всегда и без Docker.

### Последствия

- **Пароль неизбежно присутствует в argv ffmpeg внутри контейнера.**
  RTSP-мультиплексор ffmpeg не умеет передавать Basic-креденшелы вне URL (`-headers` работает только для HTTP).
  Митигации: пароль только в переменной окружения, никогда в `docker-compose.yml` и никогда в argv скрипта-обёртки; в
  лог уходит URL с заменой пароля на `***`; уровень логов ffmpeg зафиксирован на `error` (на `verbose` ffmpeg печатает
  URL целиком) и это закреплено тестом. Остаточная экспозиция — `ps` внутри контейнера и
  `docker inspect`.
- **Публиковать можно только в пути, описанные в `mediamtx.yml`.** Catch-all пути нет: публикация в необъявленный путь
  отвергается с `400 Bad Request`. В dev объявлены `cam1` и `live`, в production — только `cam1`, поэтому многопоточный
  сценарий возможен лишь локально. Обёртка проверяет список путей заранее и перечисляет доступные.
- **Непрерывная публикация наполняет `recordings/`** со скоростью ≈ 11 МБ/мин на поток при битрейте 1500k. Обёртка
  печатает оценку при старте, сквозная проверка использует облегчённый источник (640x480@15, 500k) и снимает имитатор
  через `trap EXIT`.
- Профиль становится новым механизмом гейтинга, чей отказ означает поставку фальш-камеры в production. Поэтому он
  закреплён сразу тремя способами:
  `test_simulator_is_profile_gated`, `test_production_deploy_does_not_enable_the_profile`
  и проверка в `scripts/healthcheck.sh`, считающая наличие контейнера на сервере ошибкой.
- Появляется неявная связка с ffmpeg-сборкой MediaMTX: обновление тега образа меняет и сервер, и клиента одновременно.
  Это считается приемлемым — версии и так обязаны быть согласованы, а `test_simulator_shares_the_mediamtx_image`
  не даёт им разойтись.

### Альтернативы

- **`ffmpeg` на хосте через `scripts/simulate-stream.sh`** — отклонено как единственный механизм: требует установленного
  ffmpeg (на Windows его обычно нет) и упирается в `TACITUS_MTX_RTSP_BIND=127.0.0.1`, из-за чего работает только на
  машине деплоя. Скрипт сохранён, но как обёртка над сервисом.
- **Отдельный образ `jrottenberg/ffmpeg` или `linuxserver/ffmpeg`** — отклонено: новая запись в цепочке поставок и
  второй ffmpeg, расходящийся с тем, что использует MediaMTX, ради возможности, которая уже есть.
- **Несколько реплик через `--scale`** — отклонено: несовместимо с
  `container_name`, который задают все остальные сервисы. Несколько потоков делаются перечислением путей в
  `TACITUS_SIM_PATHS`.
- **Постоянный сервис для негативного сценария** — отклонено: проверка «MediaMTX обязан отказать» одноразовая по смыслу,
  поэтому выполняется через
  `docker compose run --rm`.
- **Пробный файл-фикстура вместо `testsrc2`** — отклонено: потребовал бы бинарного артефакта в git ради экономии CPU,
  которой при 640x480@15 нет.

## ADR-015: Прореживание статичных кадров отдельным сервисом на образе MediaMTX

**Дата:** 2026-09-10 **Статус:** Принято

### Контекст

Камера, смотрящая на неподвижную сцену, пишет в архив десятки тысяч кадров в час, отличающихся только шумом матрицы.
Нужно, чтобы кадров физически стало меньше — и ради объёма архива, и ради того, чтобы будущий потребитель кадров не
разбирал пустую статику.

Два факта закрывают почти все варианты:

1. **MediaMTX не декодирует видео.** Он ремуксер (`recordFormat: fmp4`), и выбросить «одинаковые» кадры на его уровне
   невозможно в принципе.
2. **Выбросить кадры без перекодирования нельзя.** P-кадры H.264 ссылаются на предыдущие, поэтому `-c:v copy` и
   прореживание несовместимы. Единственный инструмент — фильтр ffmpeg `mpdecimate` и перекодировка оставшихся кадров.

Замер на синтетике 1280x720@25, 60 с, видео без звука (`mpdecimate` с дефолтными порогами, x264 `-crf 18 -preset slow`):

| Сцена                | Кадров      | Байт              | Время |
|----------------------|-------------|-------------------|-------|
| неподвижная          | 1500 → 1    | 91 КБ → 1.8 КБ    | 2 с   |
| слабый шум матрицы   | 1500 → 1    | 12 МБ → 1.9 КБ    | 2 с   |
| сильный шум          | 1500 → 114  | 11 МБ → **19 МБ** | 14 с  |
| непрерывное движение | 1500 → 1500 | 11 МБ → **21 МБ** | 24 с  |

Первые две строки — ради чего всё делается. Последние две — почему результат обязан проверяться перед подменой: на
шумном и на подвижном источнике перекодировка честно сохраняет содержимое, и файл **растёт**.

Для сравнения, на той же неподвижной сцене увеличение GOP до 10 с без прореживания даёт 91 КБ → 75 КБ, а на слабом шуме
12 МБ → 8.8 МБ. То есть прореживание — рычаг на порядок сильнее любой настройки кодировщика.

### Решение

1. **Прореживание — отдельный сервис `recording-optimizer`** на образе
   `bluenviron/mediamtx:1.15.1-ffmpeg`, а не шаг внутри
   `scripts/mediamtx-archive-manager.py`.
2. **Обрабатываются только закрытые сегменты на диске**, до выгрузки в S3. «Закрыт» = файл не менялся
   `TACITUS_OPT_MIN_IDLE_SECONDS` (300 с).
3. **Качество — визуально без потерь** (`-crf 18`), а не математический lossless.
4. **Таймлиния сохраняется**: `-fps_mode vfr`, без `setpts`.
5. **Формат остаётся fmp4**, выход помечается тегом `tacitus_decimated=1`.
6. **Результат подменяет оригинал только пройдя все проверки**: код возврата ffmpeg, наличие кадров, длительность ±1 с,
   экономия не меньше
   `TACITUS_OPT_MIN_GAIN_PERCENT` (10 %).
7. **Сервис не за профилем compose, но выключен по умолчанию**
   (`TACITUS_OPT_ENABLED=false`).

### Обоснование

- **Почему отдельный сервис, а не шаг архиватора.** В образе `tacitus-app`
  нет ffmpeg, а в образе MediaMTX он есть — с avfilter (то есть с
  `mpdecimate`) и ffprobe, точно закреплённый, уже в стеке и уже покрытый
  `test_compose_pinning.py`. Добавить `apt-get install ffmpeg` в `tacitus-app`
  значило бы втащить медиастек в образ, на котором работает API, и разойтись с версией ffmpeg самого сервера — тот же
  довод, что в ADR-014. Разделение к тому же даёт деградацию вместо отказа: упавший или выключенный оптимизатор не
  мешает архиватору выгружать оригиналы.
- **Почему закрытые сегменты, а не поток в реальном времени.** Relay-транскодер (ffmpeg читает `rtsp://mediamtx/cam1` и
  публикует прореженный `cam1-lite`)
  стоил бы ~1 CPU на поток постоянно и удвоил бы RTSP-трафик, тогда как офлайн-обработка укладывается в секунды на
  минуту видео и не может испортить живой поток.
- **Почему CRF 18, а не lossless.** `-qp 0` даёт файл заметно больше исходного, то есть противоречит второй половине
  задачи. CRF 18 — классический порог x264 «глазом неотличимо».
- **Почему предохранитель по размеру нельзя выключить.** Две последние строки таблицы выше. Без него сервис на шумной
  камере молча раздувал бы архив, попутно теряя качество на перекодировке.
- **Почему `-fps_mode vfr`, а не `setpts`.** У выживших кадров сохраняются исходные PTS: часовая запись остаётся
  часовой. `setpts` перенумеровал бы их и превратил архив в таймлапс, сдвинув каждое событие на неверное время.
- **Почему fmp4 на выходе.** Сервер playback у MediaMTX сейчас выключен, но учётная запись `reader` право `playback`
  держит (ADR-012). Смена контейнера закрыла бы эту дверь ради удобства, которого никто не просил.
- **Почему тег в контейнере, а не файл-маркер.** `mediamtx-archive-manager.py`
  выгружает в S3 всё, что найдёт обходом каталога: маркеры уехали бы туда мусором. Тег переживает перезапуск сервиса и
  переезд файла. В mp4 он требует `-movflags +use_metadata_tags` — без флага ffmpeg молча выбрасывает неизвестный ключ,
  и каждый сегмент перекодировался бы на каждом обходе, пока от качества ничего не останется. Это закреплено тестом.
- **Почему без профиля, но выключен.** Профиль означал бы, что сервис никогда не стартует на сервере: Ansible вызывает
  compose без `--profile`
  (`ansible/roles/app_deploy/tasks/main.yml:130`). Флаг же по умолчанию `false`, потому что у развёрнутых инсталляций
  этой переменной в `.env` нет, а обновление стека не должно внезапно начинать перекодировку архива на машине, чей
  бюджет CPU считали без неё.

### Последствия

- **Перекодировка необратима.** До выгрузки в S3 существует ровно одна копия записи, и сервис её переписывает. Отсюда
  порядок проверок, атомарная подмена через `mv` и правило «при любом сомнении оригинал остаётся»: в скрипте нет ни
  одной команды, удаляющей исходный файл. Закреплено
  `test_script_never_deletes_a_recording` и
  `test_replacement_happens_only_after_every_check`.
- **Появляется общий с архиватором порог «сегмент закрыт».**
  `mediamtx-archive-manager.py` теперь читает `MIN_IDLE_SECONDS` и пропускает как свежие файлы, так и временные файлы
  оптимизатора (`.<имя>.tacitus.tmp`). Побочно это чинит существовавший дефект: size-based ветка сортировала файлы по
  возрасту и при переполнении диска могла выгрузить и удалить сегмент, который MediaMTX пишет прямо сейчас.
- **Возраст файла переносится на результат** (`touch -r`). Без этого подмена молодила бы каждую запись, и архив не
  уезжал бы в S3 никогда.
- **Прореженное видео становится VFR.** Длительность и таймлиния сохранены и проверяются, но покадровая перемотка в
  плеере по такому файлу ведёт себя иначе, чем по CFR-записи.
- **Выигрыш непредсказуем до замера на конкретной камере.** Он определяется шумом матрицы, а не сценой: диапазон от
  «выброшено всё» до «не выброшено ничего». Поэтому пороги `hi`/`lo`/`frac` вынесены в переменные окружения, а включение
  сервиса — осознанное действие оператора.
- **Перекодировка — единственная тяжёлая по CPU работа в стеке.** Контейнер получил собственный лимит (`2.0`), ffmpeg
  внутри запускается под `nice`, а MediaMTX ограничен своим `1.0` — приём потока оптимизатор задушить не может.

### Альтернативы

- **Шаг транскодирования внутри `mediamtx-archive-manager.py`** — отклонено:
  потребовало бы ffmpeg в образе приложения (см. обоснование) и связало бы выгрузку в S3 с многоминутной перекодировкой
  в одном цикле.
- **Relay-транскодер в реальном времени** (`cam1` → `cam1-lite`) — отклонено:
  ~1 CPU на поток постоянно, удвоенный RTSP-трафик и риск для живого потока ради того же результата.
- **Отказ от записи, пока нет движения** (детектор дёргает `record: yes/no`
  через Control API) — отклонено на этом шаге: экономия ещё больше, но кадры до события теряются безвозвратно, а это уже
  смена требований к архиву, а не оптимизация.
- **Только увеличение GOP и снижение битрейта** — отклонено как замена: даёт единицы-десятки процентов там, где
  прореживание даёт два порядка, и вообще не уменьшает число кадров, то есть решает половину задачи.
- **Математический lossless (`-qp 0`)** — отклонено: файл становится больше исходного.

## ADR-016: Обрезка кадра переписыванием conformance window вместо перекодирования

**Дата:** 2026-09-10 **Статус:** Принято

### Контекст

У камер часть кадра не несёт полезной информации: небо, земля, потолок, полоса со служебным OSD-таймштампом. Нужно
срезать её у записей, причём доля своя для каждой камеры.

Обрезка кадра — операция фильтра (`-vf crop`), а фильтр требует декодирования и обратного кодирования. Для часовых
сегментов со всех камер это самая дорогая работа в стеке, и она необратимо портит качество.

Но H.264 и H.265 несут в SPS «conformance window» — прямоугольник, который декодер обязан отрезать при выводе. Он
существует, потому что кодек кодирует целые макроблоки: камера 1080p физически кодирует 1088 строк и объявляет 8 из них
отрезанными. ffmpeg умеет переписывать это окно битстрим-фильтром (`h264_metadata` / `hevc_metadata`) при `-c copy`.

### Решение

Обрезать записанные сегменты переписыванием conformance window, без перекодирования. Отдельный сервис `video-processor`
на собственном образе (`Dockerfile.video-processor`), доли обрезки — в таблице `streams`, правятся через
`/stream-configs` и веб-интерфейс.

### Последствия

- Обработка сегмента — ремукс: секунды вместо минут, нулевая потеря качества, размер файла не меняется.
- **Механизм не является средством сокрытия.** Срезанные пиксели остаются в файле и восстанавливаются сбросом crop-окна.
  Для приватных зон он неприменим, и веб-интерфейс обязан об этом предупреждать. Если такая задача появится, её решает
  отдельный механизм с настоящим перекодированием.
- Живой RTSP-поток остаётся полным: обрезаются только записи.
- В проекте появляется третий ffmpeg (Debian-сборка против 6.1.2 в образе MediaMTX). Расхождение версий вынесено в
  `docs/infrastructure.md` и
  `docs/upgrades.md`.

### Что пришлось учесть

Замер на реальных сегментах MediaMTX (1920x1080, H.264 + AAC) вскрыл три вещи, без которых реализация была бы неверной:

1. **Смещения абсолютны относительно кодированного кадра, а не добавляются к отображаемому.** Наивные 15 % / 20 % от
   1080 дают 710 видимых строк вместо 702: паддинг в 8 строк надо прибавить к нижнему смещению.
2. **Кодированную высоту узнать нечем.** `ffprobe` её не сообщает, а в сегментах MediaMTX её нет вовсе; попытки вытащить
   её дешёвым зондом (`-frames:v 1`, `-t 0.3`, сброс окна в ноль) дают отображаемую высоту. Поэтому паддинг вычисляется
   из выравнивания по макроблокам (`ceil(H/16)*16 - H`) и **проверяется** по фактической высоте результата, с одной
   самокорректирующейся повторной попыткой.
3. **Пересчёт не идемпотентен, хотя применение фильтра идемпотентно.** Повтор с теми же абсолютными смещениями — no-op,
   но проценты, посчитанные от уже обрезанного кадра, режут второй раз. Поэтому в контейнер пишется маркер
   `tacitus_crop=v1:<сверху>:<снизу>:<исходная высота>:<паддинг>`. Он хранит исходную геометрию, и от неё
   пересчитывается всё последующее — включая отключение обрезки, восстанавливающее полный кадр, хотя исходного файла уже
   нет.

Маркер пишется с `-movflags +use_metadata_tags`: без него mp4-муксер молча выбрасывает все нестандартные теги, включая
`tacitus_decimated` из ADR-015.

### Альтернативы

- **Перекодирование (`-vf crop`)** — отклонено как основной механизм: цена по CPU несопоставима с задачей «убрать небо
  из кадра», плюс потеря качества. Остаётся единственным вариантом, если понадобится настоящее сокрытие зон.
- **Обрезка живого потока через `runOnReady`** — отклонено: перекодирование 24/7 на каждую камеру, задержка, и нагрузка
  ложится на контейнер приёма потока, который нельзя ставить под удар.
- **Обрезка на выдаче** — отклонено: платить CPU за каждый просмотр вместо одного прохода по сегменту.
- **Хранение долей обрезки в конфиг-файле** — отклонено в пользу таблицы
  `streams`: настройка меняется оператором через интерфейс, а не правкой файла с перезапуском контейнера.
- **Свой разбор SPS ради точной кодированной высоты** — отклонено: проверка результата по факту закрывает ту же задачу
  без Exp-Golomb-парсера в проде.

## ADR-017: Единый источник версии в коде и её выдача только аутентифицированному клиенту

**Дата:** 2026-09-10 **Статус:** Принято

### Контекст

Версия сервиса не была видна ниоткуда, кроме исходников: `FastAPI()` создавался без `version=`, во фронтенде строки
«версия» не было вовсе, а `app.__version__` использовался единственным потребителем — как release для Sentry. При этом
число `0.1.0` уже было продублировано в восьми местах (метаданные пакета, два файла пакетов фронтенда, пять тегов
образов в compose, переменная развертывания, примеры в документации), и синхронизировано было ровно одно из них.

Образы собираются на сервере развёртывания, `.git` туда не копируется, реестра образов нет. Поэтому у оператора не было
способа узнать, какая сборка сейчас работает, не заходя в контейнер.

### Решение

Версия объявляется в `app/__init__.py` и остаётся значением исполняемого кода, а не переменной окружения. Остальные
места — производные копии; `scripts/bump_version.py` переписывает их все за одно действие, а
`tests/test_version_consistency.py` читает перечень мест из того же скрипта и падает при расхождении.

Наружу версия отдаётся ресурсом `GET /settings/version`, доступным только аутентифицированному пользователю, и
показывается в шапке каждого раздела веб-интерфейса. Дополнительно версия попадает в OpenAPI и в первую строку журнала
при старте процесса.

### Обоснование

- Версия характеризует сборку, а не установку: переменная окружения позволила бы объявить одну версию, а запустить
  другую, то есть ровно ту ложь, ради устранения которой это делается.
- Перечень мест объявления и средство их обновления живут в одном файле: место, добавленное однажды, и обновляется, и
  проверяется. Разъехавшаяся копия не ломает ничего немедленно — только заставляет установку врать о себе, поэтому
  нужен тест, а не внимательность.
- Точный номер сборки — прямая подсказка для подбора известных уязвимостей. Требование 8.1.3 ТЗ уже запрещает
  раскрывать внутренние детали реализации анонимному клиенту, и версия ничем не отличается: тот, кому она нужна для
  эксплуатации, уже прошёл аутентификацию.
- `GET /health` остаётся анонимным и неизменным: это признак работоспособности для балансировщика и оркестратора, и
  добавлять в него сведения о сборке — значит раскрыть их всем.

### Последствия

- Обновление версии — одна команда; ручная правка любого из мест ловится тестом.
- Версия видна из браузера, но не видна до входа и не видна анонимному сканеру.
- Ресурс версии не логируется: интерфейс запрашивает его на каждом разделе, а сведений о развёртывании он не
  раскрывает — в отличие от `GET /settings`, доступ к которому фиксируется.

### Альтернативы

- **Расширить анонимный `/health` полем версии** — отклонено: самое дешёвое решение ценой раскрытия версии сборки всем,
  кто может дотянуться до порта.
- **Версия из метаданных пакета (`importlib.metadata`)** — неприменимо: образ копирует `app/`, а не устанавливает
  дистрибутив, поэтому в контейнере метаданных нет.
- **Версия переменной окружения (`TACITUS_APP_VERSION`)** — отклонено: разрывает связь между кодом и тем, что он о себе
  сообщает.
- **Git-хеш и время сборки в дополнение к номеру** — отклонено на текущем этапе: требует сквозного проброса
  `ARG` → `build.args` → extra-vars через Dockerfile, compose и Ansible ради сведений, которые нужны при отладке
  конкретной сборки, а не в повседневной работе. Возвращаться к этому имеет смысл, если между релизами начнёт
  выкладываться несколько сборок одной версии.

## ADR-018: Доступ к архиву записей отдельным ресурсом с ключом-путём

**Дата:** 2026-09-10 **Статус:** Принято

### Контекст

Процесс ротации выгружает записи в объектное хранилище ключами вида
`mediamtx-archives/cam1/2026-09-10_12-00-00-000000.mp4` и удаляет локальные копии. Хранилище у записей и
пользовательских файлов одно, поэтому `GET /files/` эти ключи перечисляет — но получить по ним объект было нельзя:
параметр пути `{filename}` не сопоставляется со значением, содержащим `/`, а `sanitize_filename()` сводит имя к
basename и вместе со структурой каталога теряет адрес объекта. Цикл «поток → запись → архив → выдача» обрывался на
последнем шаге: запись, попавшая в архив, не возвращалась никогда.

Контракт `/files` при этом рассчитан на другое: плоское имя, белый список типов содержимого и расширений, ограничение
размера загрузки. Записи не загружаются через API, их имена задаёт медиасервер, а их тип в белый список не входит.

### Решение

Архив выдаётся отдельным ресурсом `/recordings` над тем же bucket:

- идентификатор записи — её ключ целиком, включая префикс архива, и принимается как `{key:path}`;
- ключ проверяет `sanitize_object_key()`: посегментный разбор с запретом `..`, `.`, пустых сегментов, скрытых имён и
  символов вне `[a-zA-Z0-9._-]`, и только затем — обязательный префикс архива;
- префикс задаётся `TACITUS_S3_ARCHIVE_PREFIX` и нормализуется при старте до вида с завершающим `/`;
- перечень возвращается страницами: continuation token хранилища отдаётся клиенту как непрозрачный `next_cursor`;
- отбор по потоку сужает префикс запроса к хранилищу, а не фильтрует полученный ответ;
- выдача ссылки и удаление записываются в журнал безопасности как `recording.download` и `recording.delete`.

`/files` остаётся как есть.

### Обоснование

- Плоское имя и путь — разные контракты с разными правилами проверки. Попытка обслужить оба одним параметром означала
  бы ослабление проверки для файлов ради записей: `sanitize_filename` пришлось бы научить пропускать `/`.
- Пока bucket общий, префикс — единственная граница между архивом и пользовательскими файлами. Поэтому он не
  «настройка пути», а предмет проверки: без завершающего `/` соседний префикс `mediamtx-archives-old/` прошёл бы
  проверку `startswith`, предназначенную для `mediamtx-archives/`.
- Проверка префикса идёт последней намеренно: попытка обхода получает ответ «path traversal», и в журнале видно, что
  именно пробовали сделать, а не только то, что ключ оказался чужим.
- Сплошной обход хранилища, как в `GET /files/`, для архива неприменим: он растёт на сегмент в час на каждый поток, и
  время ответа стало бы функцией от того, как давно сервис пишет записи. Постраничная выдача переносит эту границу на
  сторону хранилища, которое умеет отдавать страницу за постоянное время.
- Отбор по потоку на стороне хранилища, а не в приложении: фильтрация после выборки означала бы, что страница из ста
  ключей может не содержать ни одного нужного, и клиент вынужден листать весь архив, чтобы найти записи одной камеры.

### Последствия

- Записи, уехавшие в архив, доступны через API: перечень, ссылка, удаление.
- Удаление через API необратимо — локальной копии к этому моменту уже нет.
- Перечни разделены: `GET /files/` показывает только корень bucket, `GET /recordings` — только архив. Ни один ресурс не
  перечисляет объекты, которые не может выдать.
- Появился второй путь к объектам хранилища, и правило «проверять ключ» теперь существует в двух видах:
  `sanitize_filename` для файлов и `sanitize_object_key` для записей. Оба покрыты негативными тестами, потому что
  ошибка в любом из них открывает доступ к чужим объектам того же bucket.

### Альтернативы

- **Расширить `/files/{filename}` до `{filename:path}`** — отклонено: одна проверка на два контракта, причём ослабление
  затронуло бы и загрузку файлов, где алфавит без `/` — часть защиты.
- **Кодировать ключ в base64 и передавать плоской строкой** — отклонено: адрес объекта перестаёт быть читаемым в
  журналах и в адресной строке, а проверка префикса всё равно нужна после декодирования — то есть цена есть, а защиты
  не прибавляется.
- **Отдельный bucket для архива** — отложено: снимает необходимость в проверке префикса, но требует второго набора
  политик доступа и миграции уже выгруженных записей. Имеет смысл при появлении требований к раздельному хранению или
  ретеншну.
- **Перечень записей из базы данных вместо хранилища** — отклонено: потребовало бы таблицы, которую заполняет процесс
  ротации, то есть второго источника правды о содержимом bucket и нового класса расхождений «в базе есть, в хранилище
  нет».

## ADR-019: Постраничные перечни хранилища и разделение файлов и записей разделителем

**Дата:** 2026-09-10 **Статус:** Принято

### Контекст

`GET /files/` обходил bucket целиком по continuation token и отдавал все ключи одним ответом. Пока в хранилище лежали
только загруженные файлы, это было незаметно. С архивом записей в том же bucket выдача стала расти на сегмент в час на
каждый поток: ответ на запрос страницы «Файлы» — это весь архив, а вместе с ним и объекты, которые ресурс файлов всё
равно не может ни выдать, ни удалить (ADR-018).

Отбор архива по префиксу решает вторую половину задачи, но не первую: ключи в хранилище отсортированы лексикографически,
архив занимает в этом порядке непрерывный участок, и отбрасывание его ключей в приложении означает, что клиент листает
их по сто штук за запрос, получая пустые страницы, — только чтобы добраться до файлов, отсортированных после архива.

### Решение

Перечень файлов запрашивается у хранилища с разделителем `/` и отдаётся страницами:

- разделитель сворачивает всё вложенное в common prefixes, и архив не попадает в ответ — при этом стоит одну запись
  страницы, а не тысячи;
- файлами считаются объекты в корне bucket — ровно то, что способна создать загрузка: `sanitize_filename` не пропускает
  `/` в имени;
- страница ограничена `limit` (1–1000, по умолчанию 100), продолжение — непрозрачный `next_cursor`, тот же контракт, что
  у `/recordings`;
- сводная статистика по-прежнему обходит bucket целиком, но считает файлы и архив раздельно.

### Обоснование

- Разделитель переносит отбор на сторону хранилища, где он бесплатен. Это единственный способ сделать цену страницы
  независимой от размера архива, не изобретая собственную схему курсоров с перескоком через диапазон ключей.
- Определение «файл — объект в корне» не выдумано ради реализации: оно совпадает с тем, что сервис умеет создавать и
  адресовать. Ресурс, который перечисляет объекты, недоступные ни для скачивания, ни для удаления, вводит пользователя в
  заблуждение.
- Сводка остаётся сплошным обходом: итог по определению не бьётся на страницы, и подменить его курсором нечем. Но
  показатели файлов и архива в ней разделены — иначе счётчик рядом со списком из двух файлов показывал бы десятки тысяч
  объектов.
- Контракт пагинации одинаков у `/files` и `/recordings`: один и тот же клиентский код, один и тот же способ отличить
  «страница кончилась» от «страница короткая».

### Последствия

- Страница может содержать меньше `limit` файлов и при этом иметь курсор: свёрнутый префикс архива хранилище засчитывает
  в размер страницы. Признак «есть ещё» — курсор, а не число элементов; это зафиксировано в схеме, в документации и в
  веб-интерфейсе.
- Объекты, помещённые в bucket посторонним способом под собственными префиксами, не попадают ни в перечень файлов, ни в
  перечень записей: сервис управляет корнем и своим архивом.
- `S3Service.list_files` возвращает пару «страница, курсор» вместо списка — сигнатура изменилась вместе со всеми
  вызывающими.

### Альтернативы

- **Отбор по префиксу архива в приложении** — отклонено: не решает стоимость обхода, а при большом архиве превращает
  листание файлов в листание архива.
- **Перескок через диапазон архива через `StartAfter`** — отклонено: даёт ту же цену страницы, что и разделитель, но
  требует собственного формата курсора (два несовместимых вида продолжения) ради случая, который разделитель закрывает
  штатным средством хранилища.
- **Отдельный bucket под архив** — отложено вместе с той же альтернативой в ADR-018.
- **Оставить сплошную выдачу и ограничить её первыми N ключами** — отклонено: молчаливое усечение, при котором клиент не
  отличает «файлов больше нет» от «сервис устал считать».

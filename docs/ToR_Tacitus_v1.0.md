# Техническое задание: сервис Tacitus

**Сервис:** Tacitus **Версия ТЗ:** 1.0 **Дата актуализации:** 2026-09-10

---

## 1. Общие сведения

### 1.1. Назначение

Tacitus — сервис приёма, записи, хранения и раздачи RTSP-видеопотоков. Сервис обеспечивает:

1. приём видеопотоков от камер и других RTSP-публикаторов;
2. непрерывную запись потоков на локальный диск;
3. автоматическую оптимизацию записей за счёт удаления кадров, не несущих изменений;
4. перенос записей в объектное хранилище S3/MinIO и освобождение локального диска;
5. выдачу файлов и архивных записей авторизованным клиентам по временным подписанным ссылкам;
6. защиту всех операций JWT-аутентификацией с журналированием security-событий.

### 1.2. Границы

В объём сервиса входит серверная часть (HTTP API), медиасервер, фоновые процессы обслуживания архива, объектное
хранилище, база данных и веб-интерфейс управления файлами и аутентификацией.

### 1.3. Вне объёма

Сервис не выполняет:

- анализ содержимого видео (детекция объектов, распознавание, аналитика);
- транскодирование живого потока в реальном времени и изменение того, что получают читатели;
- многопользовательскую модель с разграничением доступа к отдельным потокам (см. п. 3.4);
- уведомления, отчётность и биллинг.

## 2. Термины и определения

**Поток** (stream) — именованная точка, в которую публикуется видео и из которой его читают. В API медиасервера то же
самое называется `path`; наружу сервис отдаёт только слово «поток».

**Конфигурация потока** — хранимое сервисом описание потока: имя, источник, признак записи. Существует независимо от
того, публикует ли кто-то видео сейчас.

**Активный поток** — поток, о котором медиасервер сообщает своё текущее состояние: готовность, публикатор, число
читателей. Не тождественен конфигурации: сконфигурированный поток может быть неактивен, а активный — не иметь записи в
конфигурации.

**Источник** (source) — откуда берётся видео: `publisher` (присылает внешний клиент) либо URL вида `rtsp://…`, по
которому медиасервер забирает поток сам.

**Публикатор** (publisher) — тот, кто отправляет видео в поток. Также имя учётной записи медиасервера с правом
`publish`.

**Читатель** (reader) — тот, кто получает видео из потока. Также имя учётной записи медиасервера с правами `read` и
`playback`.

**Запись** (recording) — видео, сохранённое медиасервером на диск в виде fmp4-сегментов. Живёт локально ограниченное
время.

**Сегмент** (segment) — один файл записи. Сегменты нарезаются по времени, а не по границам событий.

**Закрытый сегмент** — сегмент, в который медиасервер больше не пишет. Признак закрытия — отсутствие изменений файла в
течение установленного интервала.

**Прореживание** (decimation) — удаление из записи кадров, практически не отличающихся от предыдущего.

**Архив** (archive) — запись, выгруженная в S3/MinIO и удалённая с локального диска. Переход «запись → архив» необратим.

**Access-токен** — короткоживущий JWT, которым клиент подтверждает право на каждый запрос.

**Refresh-токен** — долгоживущий JWT, обмениваемый на новую пару токенов. Одноразовый: при обмене отзывается и
заменяется новым.

**Ротация** (rotation) — обмен refresh-токена на новую пару. Старый токен при этом всегда отзывается; ротация без отзыва
ротацией не считается.

**Семейство токенов** — все refresh-токены одного пользователя, связанные цепочкой ротаций. Отзывается целиком при
подозрении на кражу.

**Обнаружение повторного использования** (reuse detection) — признание refresh-токена скомпрометированным, если он
предъявлен после того, как уже был потрачен. Следствие — отзыв всего семейства.

**Отзыв** (revocation) — досрочное аннулирование токена до истечения срока. Для access-токена означает попадание его
`jti` в чёрный список, для refresh-токена — отметку времени отзыва.

**jti** — уникальный идентификатор конкретного JWT.

**Блокировка перебора** (brute-force lock) — временный отказ в аутентификации после серии неудачных попыток.

**Security-событие** — запись о значимом для безопасности действии.

**Подозрительная активность** — всплеск ответов 401/403 с одного адреса за короткое окно.

**Presigned URL** — временная подписанная ссылка на объект в S3/MinIO. Сама по себе является разрешением на скачивание.

## 3. Роли и права доступа

### 3.1. Роли HTTP API

| Роль                             | Описание                                     | Права                                                                          |
|----------------------------------|----------------------------------------------|--------------------------------------------------------------------------------|
| Анонимный клиент                 | Не предъявил валидный access-токен           | `GET /health`, `POST /auth/login`, `POST /auth/refresh`, а также `POST /auth/register`, когда регистрация включена |
| Аутентифицированный пользователь | Предъявил валидный неотозванный access-токен | Все остальные операции API                                                     |

**Требование 3.1.1.** Сервис должен отклонять с кодом 401 любой запрос к защищённому endpoint без валидного
access-токена.

**Требование 3.1.2.** Сервис должен проверять `jti` каждого предъявленного access-токена по списку отозванных и
отклонять отозванный токен, даже если его срок не истёк.

### 3.2. Учётные записи медиасервера

Доступ к RTSP разграничивается по действиям, а не по путям. Сервис должен объявлять ровно три учётные записи:

| Учётная запись | Действия           | Назначение                          |
|----------------|--------------------|-------------------------------------|
| `publisher`    | `publish`          | Камеры и другие публикаторы         |
| `reader`       | `read`, `playback` | Потребители живого потока и записей |
| `tacitus-api`  | `api`              | Обращения бэкенда к Control API     |

**Требование 3.2.1.** Публикатор не должен иметь права читать, читатель — права публиковать, ни один из них — доступа к
Control API.

**Требование 3.2.2.** Сервис должен явно объявлять список учётных записей. Отсутствие объявления включает встроенную
анонимную запись с полными правами на все пути и недопустимо.

### 3.3. Аутентификация служебных процессов

**Требование 3.3.1.** Фоновые процессы обслуживания архива не должны иметь доступа к секретам, не нужным для их работы:
процесс, обрабатывающий файлы записей, не получает ни ключей объектного хранилища, ни пароля базы данных, ни секрета
подписи токенов.

### 3.4. Ограничение модели доступа

**Требование 3.4.1.** Права на потоки не разграничиваются между пользователями сервиса: любой аутентифицированный
пользователь видит состояние всех потоков. Разграничение доступа к RTSP определяется учётными записями медиасервера (п.
3.2), а не пользователями API.

## 4. Функциональные требования

### 4.1. Аутентификация и управление сессиями

**Требование 4.1.1.** Сервис должен регистрировать пользователя по имени и паролю, сохраняя только хеш пароля
(`pbkdf2_sha256`).

**Требование 4.1.2.** Сервис должен выдавать при успешном входе пару «access-токен + refresh-токен».

**Требование 4.1.3.** Сервис должен обменивать refresh-токен на новую пару, отзывая предъявленный токен в той же
операции.

**Требование 4.1.4.** Сервис должен распознавать повторное предъявление уже потраченного refresh-токена как
компрометацию и отзывать всё семейство токенов пользователя.

**Требование 4.1.5.** Сервис должен хранить только SHA-256 хеш refresh-токена, но не сам токен.

**Требование 4.1.6.** Сервис должен отзывать access-токен при выходе, сохраняя его `jti` до момента естественного
истечения.

**Требование 4.1.7.** Сервис должен блокировать аутентификацию после серии неудачных попыток. Порогов два: на пару «имя
пользователя + IP» и на имя пользователя со всех адресов сразу.

**Требование 4.1.8.** Время ответа на попытку входа не должно позволять отличить несуществующего пользователя от
неверного пароля.

**Требование 4.1.9.** Признак активности учётной записи проверяется не только при входе, но и при каждом обращении с
access-токеном и при каждой ротации refresh-токена. Отключение учётной записи прекращает её действующие сессии и
исключает их продление.

**Требование 4.1.10.** Токен, ссылающийся на несуществующую учётную запись, отклоняется наравне с токеном отключённой.

### 4.2. Приём и запись потоков

**Требование 4.2.1.** Сервис должен принимать видео по RTSP от публикаторов, предъявивших учётные данные с правом
`publish`.

**Требование 4.2.2.** Сервис должен принимать публикацию только в явно объявленные потоки. Публикация в необъявленный
поток отклоняется.

**Требование 4.2.3.** Сервис должен вести непрерывную запись принимаемых потоков на локальный диск в формате fmp4,
нарезая её на сегменты фиксированной длительности.

**Требование 4.2.4.** Сервис должен именовать файлы записей так, чтобы имя однозначно определяло поток и момент начала
сегмента.

### 4.3. Прореживание записей

**Требование 4.3.1.** Сервис должен уменьшать число кадров в закрытых сегментах записи, удаляя кадры, практически не
отличающиеся от предыдущего.

**Требование 4.3.2.** Прореживание должно применяться только к закрытым сегментам. Сегмент, в который ведётся запись,
обрабатываться не должен.

**Требование 4.3.3.** Прореживание должно сохранять таймлинию записи:
длительность обработанного сегмента совпадает с исходной, а оставшиеся кадры сохраняют исходные временные метки. Сжатие
записи в ускоренную (таймлапс)
недопустимо.

**Требование 4.3.4.** Прореживание не должно изменять звуковую дорожку и формат контейнера.

**Требование 4.3.5.** Качество оставшихся кадров должно оставаться визуально неотличимым от исходного.

**Требование 4.3.6.** Результат обработки должен замещать исходный сегмент только после подтверждения всех условий:

1. обработка завершилась успешно;
2. в результате присутствует хотя бы один видеокадр;
3. длительность отличается от исходной не более чем на установленный допуск;
4. размер файла меньше исходного не менее чем на установленную долю;
5. исходный сегмент на момент замещения по-прежнему присутствует на диске.

При невыполнении любого условия результат отбрасывается, а исходный сегмент остаётся неизменным.

**Требование 4.3.7.** Замещение сегмента должно быть атомарным.

**Требование 4.3.8.** Обработанный сегмент должен нести признак обработки, исключающий повторную обработку при
последующих обходах.

**Требование 4.3.9.** Возраст исходного сегмента должен переноситься на результат: обработка не изменяет момент, с
которого отсчитывается срок хранения записи.

**Требование 4.3.10.** Прореживание должно быть отключаемым и по умолчанию выключено.

**Требование 4.3.11.** Незавершённые результаты обработки, оставшиеся после аварийного останова, должны удаляться при
следующем запуске.

### 4.4. Ротация и архивирование записей

**Требование 4.4.1.** Сервис должен переносить в объектное хранилище записи старше установленного срока и удалять их
локальные копии.

**Требование 4.4.2.** Сервис должен переносить в объектное хранилище наиболее старые записи при превышении
установленного суммарного объёма локального каталога, пока объём не опустится до предела.

**Требование 4.4.3.** Локальная копия должна удаляться только после подтверждённой успешной выгрузки.

**Требование 4.4.4.** Ротация не должна затрагивать сегмент, в который ведётся запись, и промежуточные файлы обработки
записей.

**Требование 4.4.5.** Сервис должен предоставлять аутентифицированному пользователю перечень записей, перенесённых в
объектное хранилище, выдачу ссылки на скачивание записи и её удаление. Перенос в архив не должен делать запись
недоступной.

**Требование 4.4.6.** Записи и пользовательские файлы размещаются в одном хранилище и разделяются префиксом ключа.
Префикс задаётся параметром окружения и должен совпадать с префиксом, который использует процесс ротации.

**Требование 4.4.7.** Ключ записи, поступивший от клиента, должен проверяться посегментно: выход за пределы префикса
архива, переход к родительскому каталогу и символы вне заданного алфавита должны отклоняться как ошибка запроса. Ключ,
не прошедший проверку, не должен передаваться в хранилище.

**Требование 4.4.8.** Удаление записи из объектного хранилища необратимо: локальная копия к этому моменту уже удалена
(требование 4.4.3), и объект в хранилище — единственный экземпляр.

### 4.5. Состояние потоков

**Требование 4.5.1.** Сервис должен предоставлять перечень активных потоков с указанием готовности, состава дорожек,
объёма принятых данных и числа читателей.

**Требование 4.5.2.** Сервис должен предоставлять состояние отдельного потока по его имени.

**Требование 4.5.3.** Имя потока, поступившее от клиента, должно проверяться на допустимый алфавит до подстановки в
обращение к медиасерверу.

**Требование 4.5.4.** Недоступность медиасервера должна возвращаться клиенту как ошибка сервиса, а не как пустой
перечень потоков.

### 4.6. Работа с файлами

**Требование 4.6.1.** Сервис должен предоставлять аутентифицированному пользователю перечень объектов хранилища,
загрузку файла, удаление файла, сводную статистику хранилища и выдачу ссылки на скачивание.

**Требование 4.6.2.** Скачивание должно выполняться по временной подписанной ссылке, выдаваемой только
аутентифицированному пользователю.

**Требование 4.6.3.** Имя файла, поступившее от клиента, должно санитизироваться; выход за пределы каталога хранилища
должен быть невозможен.

**Требование 4.6.4.** Сервис должен ограничивать размер загружаемого файла и перечень допустимых типов содержимого.

**Требование 4.6.5.** Перечень файлов возвращается страницами по правилам требований 8.10.2 и 8.10.3. Сплошная выдача
всех объектов хранилища одним ответом не допускается.

**Требование 4.6.6.** Перечень файлов и перечень записей не должны пересекаться. Файлами считаются объекты в корне
хранилища — именно те, которые создаёт загрузка; всё вложенное, включая архив записей, из перечня файлов исключается на
стороне хранилища, а не отбором полученного ответа.

**Требование 4.6.7.** Сводная статистика хранилища должна приводить показатели файлов и показатели архива записей
раздельно: объём, число объектов и наибольший объект считаются по тому набору, который перечисляет ресурс файлов.

### 4.7. Веб-интерфейс

**Требование 4.7.1.** Веб-интерфейс должен обеспечивать вход по имени и паролю и работу с файлами хранилища: перечень,
загрузку, скачивание, удаление.

**Требование 4.7.2.** Веб-интерфейс должен выполнять ротацию токенов прозрачно для пользователя и переводить его на
форму входа при исчерпании сессии.

**Требование 4.7.3.** Веб-интерфейс должен предоставлять отдельный раздел просмотра действующей конфигурации: перечень
переменных окружения приложения с их текущими значениями, сгруппированный по подсистемам, с отбором по имени и значению.

**Требование 4.7.4.** Раздел просмотра конфигурации доступен только для чтения. Изменение параметра выполняется правкой
окружения и перезапуском сервиса.

**Требование 4.7.5.** Значения, являющиеся секретами, в веб-интерфейсе не отображаются. Для них показывается только
признак того, задано значение или нет.

**Требование 4.7.6.** Веб-интерфейс должен отображать версию работающего сервиса в заголовке каждого раздела,
доступного аутентифицированному пользователю. Версия запрашивается у сервиса; при недоступности сведений заголовок
отображается без неё и остаётся работоспособным.

**Требование 4.7.7.** Раздел файлов должен загружать перечень постранично и позволять дозагрузку следующей страницы по
явному действию пользователя. Признаком наличия следующей страницы служит указатель продолжения, а не число элементов в
полученной странице.

**Требование 4.7.8.** Раздел файлов должен показывать показатели архива записей отдельной величиной, не смешивая их с
показателями файлов.

### 4.8. Обрезка кадра записей

**Требование 4.8.1.** Сервис должен срезать в закрытых сегментах записи заданную долю кадра сверху и снизу, замещая
исходный сегмент результатом.

**Требование 4.8.2.** Доли обрезки должны задаваться отдельно для каждого потока и изменяться через HTTP API и
веб-интерфейс.

**Требование 4.8.3.** Обрезка должна применяться только к закрытым сегментам. Сегмент, в который ведётся запись,
обрабатываться не должен.

**Требование 4.8.4.** Обрезка не должна перекодировать видео: срезается область отображения кадра, а закодированные
кадры копируются без изменений. Потеря качества и изменение звуковой дорожки недопустимы.

**Требование 4.8.5.** Обрезка не является средством сокрытия сведений. Срезанная область остаётся в файле и может быть
восстановлена, о чём пользователь должен быть уведомлён в веб-интерфейсе. Для сокрытия областей кадра механизм
неприменим.

**Требование 4.8.6.** Обрабатываться должны потоки, для которых обрезка включена. Записи потоков без конфигурации не
должны изменяться.

**Требование 4.8.7.** Результат должен замещать исходный сегмент только после подтверждения всех условий:

1. обработка завершилась успешно;
2. результат читается как видео;
3. высота кадра результата равна расчётной;
4. исходный сегмент на момент замещения по-прежнему присутствует на диске.

При невыполнении любого условия результат отбрасывается, а исходный сегмент остаётся неизменным.

**Требование 4.8.8.** Замещение сегмента должно быть атомарным.

**Требование 4.8.9.** Обработанный сегмент должен нести признак обработки с исходной геометрией кадра. Признак должен
исключать повторную обработку при неизменных настройках и позволять пересчитать обрезку от исходной геометрии при
изменении настроек, когда исходный файл уже замещён.

**Требование 4.8.10.** Изменение долей обрезки и её отключение должны приводить к пересчёту уже обработанных сегментов;
при отключении восстанавливается полный кадр.

**Требование 4.8.11.** Возраст исходного сегмента должен переноситься на результат: обработка не изменяет момент, с
которого отсчитывается срок хранения записи.

**Требование 4.8.12.** Признаки обработки, оставленные другими процессами обработки записей, должны сохраняться в
результате.

**Требование 4.8.13.** Сегменты, кодек или развёртка которых не позволяют выполнить обрезку без перекодирования, должны
пропускаться с записью причины в журнал.

**Требование 4.8.14.** Незавершённые результаты обработки, оставшиеся после аварийного останова, должны удаляться при
следующем запуске.

### 4.9. Управление учётными записями

**Требование 4.9.1.** Приём анонимных регистраций должен управляться параметром окружения. Разграничения прав между
пользователями нет: любая созданная учётная запись получает доступ ко всем файлам, записям и конфигурациям потоков,
поэтому в развёрнутой установке регистрация выключена.

**Требование 4.9.2.** Выключение регистрации не должно лишать оператора способа завести учётную запись: создание
пользователя средством инициализации остаётся доступным независимо от этого параметра.

**Требование 4.9.3.** Сервис должен предоставлять средство отключения и повторного включения учётной записи. Отключение
дополнительно отзывает семейство refresh-токенов пользователя, чтобы повторное включение не возобновляло прежние сессии.

**Требование 4.9.4.** Попытка отключить или включить несуществующую учётную запись должна сообщаться как ошибка, а не
как успешно выполненная операция.

**Требование 4.9.5.** Пользователь должен иметь возможность сменить собственный пароль, предъявив действующий пароль
дополнительно к действующему токену.

**Требование 4.9.6.** Смена пароля прекращает все сессии пользователя: отзываются семейство refresh-токенов и
access-токен запроса, выполнившего смену. Пароль и отзывы применяются как одна операция.

**Требование 4.9.7.** Неверный действующий пароль не изменяет ни пароль, ни состояние сессий. Сессия, из которой сделана
неудачная попытка, сохраняется.

## 5. Нефункциональные требования

### 5.1. Объёмы и ретеншн

**Требование 5.1.1.** Срок локального хранения записей и предельный объём локального каталога должны быть
настраиваемыми.

**Требование 5.1.2.** Срок жизни подписанной ссылки на скачивание должен быть настраиваемым в пределах от 60 до 86 400
секунд.

**Требование 5.1.3.** Предельный размер загружаемого файла — 10 МБ; сервис отклоняет запрос, превышающий этот размер, до
его полного чтения.

### 5.2. Производительность и ресурсы

**Требование 5.2.1.** Приём и запись потоков не должны деградировать из-за фоновой обработки записей. Обработка
выполняется в отдельном контейнере с собственным ограничением по CPU и с пониженным приоритетом.

**Требование 5.2.2.** Выигрыш от прореживания определяется уровнем шума источника и не гарантируется: на источнике с
высоким уровнем шума или с непрерывным движением обработка не даёт экономии, и сегмент остаётся исходным. Пороги
чувствительности должны быть настраиваемыми.

### 5.3. Ограничение частоты запросов

**Требование 5.3.1.** Сервис должен ограничивать частоту обращений к API. Ключом ограничения служит идентификатор
пользователя, а при его отсутствии — адрес клиента.

**Требование 5.3.2.** Хранилище счётчиков должно быть настраиваемым и поддерживать общий для нескольких экземпляров
сервиса вариант.

### 5.4. Доступность

**Требование 5.4.1.** Отказ или отключение процесса обработки записей не должен препятствовать ротации и архивированию:
при его отсутствии в хранилище выгружаются исходные записи.

**Требование 5.4.2.** Сервис должен переживать временную недоступность базы данных и восстанавливать соединение без
перезапуска.

**Требование 5.4.3.** Каждый долгоживущий компонент должен предоставлять признак работоспособности, пригодный для
внешнего контроля.

**Требование 6.3.2.** Компоненты, которым требуется обработка медиаданных, должны использовать тот же образ, что и
медиасервер, не вводя в состав поставки второй набор медиабиблиотек.

**Требование 6.3.3.** Установка зависимостей во время запуска контейнера недопустима: состав каждого образа определяется
его сборкой.

**Требование 6.3.4.** Версии всех образов фиксируются точными тегами релиза.

## 7. Модель данных

Хранилище состояния — PostgreSQL. Схема управляется миграциями.

### 7.1. `streams` — конфигурации потоков

| Поле                       | Тип                    | Описание                                         |
|----------------------------|------------------------|--------------------------------------------------|
| `id`                       | integer PK             | Идентификатор                                    |
| `name`                     | varchar(64), уникально | Имя потока                                       |
| `source`                   | varchar(512)           | Источник: `publisher` либо URL                   |
| `record_enabled`           | boolean                | Признак ведения записи                           |
| `crop_enabled`             | boolean                | Признак обрезки кадра записей                    |
| `crop_top_percent`         | integer                | Доля высоты кадра, срезаемая сверху, в процентах |
| `crop_bottom_percent`      | integer                | Доля высоты кадра, срезаемая снизу, в процентах  |
| `created_at`, `updated_at` | timestamptz            | Моменты создания и изменения                     |

записями медиасервера (п. 3.2).

**Требование 7.1.2.** Доли обрезки должны храниться в процентах от высоты кадра, а не в пикселях: настройка сохраняет
смысл при замене камеры на камеру другого разрешения.

**Требование 7.1.3.** Ограничения на доли обрезки должны быть закреплены на уровне схемы хранилища, а не только на
границе HTTP: каждая доля в пределах 0..90, их сумма не более 90. Процессы обработки записей обращаются к таблице
напрямую, а обрезка замещает запись безвозвратно.

**Требование 7.1.4.** Обрезка должна быть выключена по умолчанию: появление конфигурации потока не должно приводить к
изменению уже сделанных записей.

## 8. Внешние интерфейсы

### 8.1. Общие правила

**Требование 8.1.1.** Формат обмена — JSON. Аутентификация — заголовок
`Authorization: Bearer <access-токен>`.

**Требование 8.1.2.** Каждый запрос и ответ должны нести идентификатор запроса, пригодный для сквозной корреляции в
журналах.

**Требование 8.1.3.** Тело ответа об ошибке не должно раскрывать внутренние детали реализации.

**Требование 8.1.4.** Интерактивная документация API и машиночитаемое описание схемы не публикуются в режиме
`production`. В остальных режимах они доступны без аутентификации.

### 8.2. Служебные

|-------|-----------|-----------|---------------------------|

### 8.3. Аутентификация (`/auth`)

| Метод | Путь             | Доступ       | Лимит  | Назначение                      |
|-------|------------------|--------------|--------|---------------------------------|
| POST  | `/auth/register` | Анонимный    | 3/час  | Регистрация; ответ 201 или 403  |
| POST  | `/auth/login`    | Анонимный    | 5/мин  | Вход; выдача пары токенов       |
| POST  | `/auth/refresh`  | Анонимный    | 10/мин | Ротация пары токенов            |
| POST  | `/auth/logout`   | Пользователь | 10/мин | Отзыв токенов                   |
| POST  | `/auth/password` | Пользователь | 5/мин  | Смена собственного пароля       |
| GET   | `/auth/me`       | Пользователь | 60/мин | Сведения о текущем пользователе |

**Требование 8.3.1.** Регистрация должна отключаться параметром окружения. При выключенной регистрации ресурс отвечает
кодом 403 и не создаёт учётную запись; событие фиксируется в журнале безопасности.

**Требование 8.3.2.** Смена пароля требует предъявления действующего пароля дополнительно к действующему токену.
Несовпадение отвечает кодом 400 и не изменяет ни пароль, ни состояние сессий.

**Требование 8.3.3.** Новый пароль проверяется той же политикой, что и пароль при регистрации.

**Требование 8.7.3.** Control API медиасервера не должен публиковаться за пределы внутренней сети.

### 8.8. Конфигурации потоков (`/stream-configs`)

| Метод  | Путь                     | Доступ       | Лимит  | Назначение             |
|--------|--------------------------|--------------|--------|------------------------|
| GET    | `/stream-configs`        | Пользователь | 60/мин | Перечень конфигураций  |
| POST   | `/stream-configs`        | Пользователь | 60/мин | Создание конфигурации  |
| GET    | `/stream-configs/{name}` | Пользователь | 60/мин | Конфигурация потока    |
| PATCH  | `/stream-configs/{name}` | Пользователь | 60/мин | Изменение конфигурации |
| DELETE | `/stream-configs/{name}` | Пользователь | 60/мин | Удаление конфигурации  |

**Требование 8.8.1.** Ресурс должен размещаться вне пространства имён
`/streams`: перечисление состояния потоков завершается маршрутом, принимающим произвольный путь, и вложенные маршруты в
нём недостижимы.

**Требование 8.8.2.** Создание конфигурации не объявляет поток на медиасервере. Перечень принимаемых потоков
определяется конфигурацией медиасервера; запись в таблице задаёт только обработку уже сделанных записей.

**Требование 8.8.3.** Изменение должно быть частичным: не переданные поля сохраняют текущее значение.

**Требование 8.8.4.** Совокупное ограничение на доли обрезки должно проверяться после объединения переданных полей с
сохранёнными, а не по одному запросу: доля, допустимая сама по себе, может быть недопустима поверх сохранённой.

**Требование 8.8.5.** Повторное выполнение одного и того же изменения не должно приводить к накоплению эффекта.

**Требование 8.8.6.** Удаление конфигурации не удаляет записи потока.

### 8.9. Параметры конфигурации (`/settings`)

| Метод | Путь                | Доступ       | Лимит  | Назначение                       |
|-------|---------------------|--------------|--------|----------------------------------|
| GET   | `/settings`         | Пользователь | 30/мин | Действующие параметры приложения |
| GET   | `/settings/version` | Пользователь | 60/мин | Версия работающего приложения    |

**Требование 8.9.1.** Ресурс должен возвращать перечень параметров приложения, каждый из которых содержит: имя
переменной окружения, группу отображения, значение, признак секретности и признак заданности непустого значения.

**Требование 8.9.2.** Возвращаются значения, действующие в текущем процессе, а не содержимое файла окружения: параметр,
не заданный в окружении, возвращается со значением по умолчанию, которое применяет сервис.

**Требование 8.9.3.** Значение параметра, отнесённого к секретам, не возвращается ни полностью, ни частично. Такой
параметр возвращается с пустым значением и признаком секретности.

**Требование 8.9.4.** Параметры, значением которых является адрес подключения, возвращаются без пароля: пароль
замещается маской, имя учётной записи и адрес узла сохраняются, строка параметров запроса отбрасывается.

**Требование 8.9.5.** Параметр, не отнесённый явно ни к одной группе, рассматривается как секрет.

**Требование 8.9.6.** Ресурс доступен только для чтения и не изменяет конфигурацию.

**Требование 8.9.7.** Ресурс версии должен возвращать версию сборки, из которой запущен процесс, единственным полем.
Иные сведения о сборке и среде исполнения не возвращаются.

**Требование 8.9.8.** Версия приложения не раскрывается анонимному клиенту: ресурс доступен только аутентифицированному
пользователю.

### 8.10. Записи (`/recordings`)

| Метод  | Путь                | Доступ       | Лимит  | Назначение                          |
|--------|---------------------|--------------|--------|-------------------------------------|
| GET    | `/recordings`       | Пользователь | 60/мин | Страница перечня архивных записей    |
| GET    | `/recordings/{key}` | Пользователь | 30/мин | Подписанная ссылка на запись         |
| DELETE | `/recordings/{key}` | Пользователь | 10/мин | Удаление записи из хранилища         |

**Требование 8.10.1.** Идентификатором записи служит её ключ в объектном хранилище целиком, включая префикс архива.
Ключ содержит разделители пути и передаётся как параметр пути.

**Требование 8.10.2.** Перечень возвращается страницами. Ответ содержит записи страницы и указатель на следующую
страницу; отсутствие указателя означает последнюю страницу. Размер страницы задаётся параметром запроса и ограничен
сверху пределом хранилища.

**Требование 8.10.3.** Указатель следующей страницы непрозрачен для клиента и возвращается сервису без изменений.
Указатель, отвергнутый хранилищем, обрабатывается как ошибка запроса, а не как отказ сервиса.

**Требование 8.10.4.** Перечень может ограничиваться одним потоком. Имя потока проверяется по общему правилу
(требование 4.5.3) до подстановки в обращение к хранилищу и сужает выборку на стороне хранилища.

**Требование 8.10.5.** Каждая запись перечня содержит ключ, имя потока, размер и время последнего изменения объекта.

## 11. Развертывание и эксплуатация

**Требование 11.1.** Сервис поставляется как набор контейнеров, описанный единым файлом оркестрации.

**Требование 11.2.** Развёртывание на сервер выполняется автоматизированно и не активирует необязательные профили
оркестрации. Компонент, который должен работать в production, не должен размещаться за профилем; управление им
осуществляется переменной окружения.

**Требование 11.3.** Каталог записей должен принадлежать той же учётной записи операционной системы, под которой
работают медиасервер и процессы обработки записей.

**Требование 11.4.** Миграции схемы применяются отдельным однократным процессом, завершающимся успешно до начала
обслуживания запросов.

**Требование 11.5.** Сервис должен предоставлять средство проверки состояния развёрнутого стека, перечисляющее ожидаемые
долгоживущие и однократные контейнеры и сообщающее о присутствии компонентов, не предназначенных для production.

**Требование 11.6.** Включение прореживания на конкретной установке должно быть осознанным действием оператора: значение
по умолчанию не должно менять поведение уже развёрнутых установок при обновлении.

**Требование 11.7.** Версия приложения задаётся в одном месте исполняемого кода. Метаданные пакета, файлы пакетов
фронтенда, теги собираемых образов и переменные развертывания содержат ту же версию. Версия не задаётся переменной
окружения: она характеризует сборку, а не установку.

**Требование 11.8.** Сервис должен предоставлять средство, устанавливающее версию во всех местах её объявления за одно
действие, не выполняющее операций системы контроля версий.

## 12. Требования к безопасности

### 12.1. Проверки на старте

**Требование 12.1.1.** В режиме `production` сервис должен отказываться стартовать при выполнении любого из условий:

- включён режим отладки;
- секрет подписи токенов короче 32 символов;
- используются значения по умолчанию для учётных данных объектного хранилища;
- используется значение по умолчанию для пароля Control API медиасервера;
- в списке разрешённых источников присутствует `*`.

### 12.2. Транспорт и сеть

**Требование 12.2.1.** Внешний доступ осуществляется через обратный прокси с TLS.

**Требование 12.2.2.** Порт RTSP по умолчанию публикуется только на петлевом интерфейсе: учётные данные RTSP передаются
в открытом виде, и порт должен быть доступен лишь тем узлам, которым его открыли осознанно.

**Требование 12.2.3.** Консоль объектного хранилища и Control API медиасервера не должны быть доступны извне.

**Требование 12.2.4.** Ответы обратного прокси, включая страницы ошибок, которые он формирует сам, не должны содержать
версию используемого ПО.

**Требование 12.2.5.** Отладочные артефакты сборки веб-интерфейса, раскрывающие исходный код и состав зависимостей, не
включаются в поставляемый образ.

### 12.3. Секреты

**Требование 12.3.1.** Секреты передаются только через переменные окружения и не размещаются в файлах оркестрации и в
аргументах командной строки скриптов.

**Требование 12.3.2.** Секреты не должны попадать в журналы. Уровень детализации журналов внешних утилит фиксируется
так, чтобы исключить вывод учётных данных.

**Требование 12.3.3.** Каждый компонент получает только те секреты, которые нужны для его работы.

**Требование 12.3.4.** Секреты не должны покидать процесс приложения через интерфейсы просмотра конфигурации. Отнесение
параметра к несекретным выполняется явным перечислением; параметр, не попавший в перечень, рассматривается как секрет.

### 12.4. Обработка ввода

**Требование 12.4.1.** Имена потоков и файлов, поступающие извне, должны проверяться по явно заданному алфавиту до
использования в путях и адресах.

**Требование 12.4.2.** Размер запроса ограничивается до чтения его тела.

**Требование 12.4.3.** Ключ объекта хранилища, поступивший извне, проверяется посегментно и обязан лежать внутри
разрешённого префикса. Проверка принадлежности префиксу выполняется после проверки на переход к родительскому каталогу,
чтобы попытка обхода отражалась в журнале как обход.

### 12.5. Контейнеры

**Требование 12.5.1.** Контейнеры должны работать от непривилегированной учётной записи, с корневой файловой системой
только для чтения там, где это возможно, и без избыточных привилегий.

## 13. Логирование и наблюдаемость

**Требование 13.1.** Журнал приложения должен быть структурированным и нести идентификатор запроса.

**Требование 13.2.** Сервис должен фиксировать security-события: вход, неудачную попытку входа, отзыв токена,
обнаружение повторного использования refresh-токена, выдачу файла.

**Требование 13.3.** Подозрительная активность должна сохраняться в базе; прочие security-события — в журнале.

**Требование 13.4.** Процесс обработки записей должен по каждому изменённому сегменту фиксировать одной записью: путь,
число кадров до и после, размер до и после, длительность обработки. Отказ от изменения сегмента должен фиксироваться с
указанием причины.

**Требование 13.5.** Процесс ротации должен фиксировать факт выгрузки каждого файла и итоговый объём локального
каталога.

**Требование 13.6.** При старте приложение должно фиксировать в журнале собственную версию и профиль запуска.

## 14. Требования к тестированию и приемке

**Требование 14.1.** Автоматические проверки должны выполняться без внешних зависимостей и без контейнерной среды.
Проверка, молча пропускающаяся при отсутствии окружения, не считается проверкой.

**Требование 14.2.** Автоматическими проверками должны быть закреплены:

1. отсутствие установки зависимостей при старте контейнеров;
2. фиксация версий образов точными тегами;
3. установка зависимостей приложения только из файла блокировки с проверкой хешей;
4. недоступность защищённых endpoint без валидного токена;
5. отзыв и ротация токенов, включая обнаружение повторного использования;
6. поведение ротации записей на границах срока и объёма;
7. невыгружаемость незакрытых сегментов и промежуточных файлов обработки;
8. свойства процесса обработки записей: отсутствие операций удаления исходного сегмента, замещение только после всех
   проверок, невозможность отключить проверку экономии, перенос возраста файла, сохранение таймлинии;
9. изоляция компонентов от чужих секретов;
10. недоступность необязательных компонентов в production;
11. отсутствие значений секретов в ответе ресурса просмотра конфигурации и полнота отнесения параметров приложения к
    группам;
12. единство версии приложения во всех местах её объявления: версия исполняемого кода, метаданные пакета, файлы
    пакетов фронтенда, теги собираемых образов и переменные развертывания.

**Требование 14.3.** Приёмка конвейера приёма видео выполняется сквозной проверкой: публикация потока → появление потока
в перечне → появление сегмента записи → выгрузка в объектное хранилище.

**Требование 14.4.** Приёмка прореживания выполняется на двух источниках:
неподвижном (число кадров сокращается, длительность сохраняется, признак обработки проставлен) и подвижном (экономии
нет, исходный сегмент не изменён).

## 15. Ограничения и допущения

**Ограничение 15.1.** Медиасервер не декодирует видео. Уменьшение числа кадров принципиально невозможно без
декодирования и повторного кодирования, поэтому выполняется отдельным компонентом и только над закрытыми сегментами.

**Ограничение 15.2.** Прореживание необратимо: до выгрузки в объектное хранилище существует единственная копия записи.
Этим продиктованы порядок проверок (п. 4.3.6) и правило сохранения исходного сегмента при любом сомнении.

**Ограничение 15.3.** Прореженная запись имеет переменную частоту кадров. Длительность и таймлиния сохраняются, но
покадровая навигация по такой записи отличается от навигации по записи с постоянной частотой кадров.

**Ограничение 15.4.** Выигрыш от прореживания не может быть определён заранее:
он зависит от уровня шума источника. Допускается, что на части установок обработка не даст экономии и все сегменты
останутся исходными.

**Ограничение 15.5.** Учётные данные RTSP передаются в открытом виде; шифрование транспорта RTSP не применяется.
Компенсируется ограничением доступности порта (п. 12.2.2).

**Ограничение 15.6.** Учётные данные публикации неизбежно присутствуют в аргументах процесса публикатора внутри его
контейнера.

**Ограничение 15.7.** Права на потоки не разграничиваются между пользователями API (п. 3.4).

**Допущение 15.8.** Публикаторы (камеры) доступны в сети, где порт RTSP открыт осознанно, и используют учётные данные с
правом `publish`.

**Допущение 15.9.** Объектное хранилище обладает достаточным объёмом для долговременного хранения архива: ретеншн
ограничивает локальный диск, но не хранилище.

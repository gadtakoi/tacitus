# Инфраструктура

## Docker Compose

```yaml
services:
  app:              # FastAPI (Uvicorn)
  nginx:            # Reverse proxy + static files
  postgres:         # PostgreSQL 18 — пользователи, токены, security-события
  db-migrations:    # Alembic upgrade head (init container, Exit 0)
  redis:            # Хранилище счётчиков rate limiting
  minio:            # S3-compatible storage
  minio-init:       # Bucket provisioning (init container, Exit 0)
  mediamtx:         # RTSP сервер и запись потоков
  mediamtx-cleanup: # Ротация записей и выгрузка старых сегментов в S3
```

Порядок запуска задан через `depends_on` с условиями: `app` стартует только
после `service_healthy` у `postgres` и `minio` и `service_completed_successfully`
у `minio-init` и `db-migrations`.

## PostgreSQL

- Образ `postgres:18.6-alpine` (точный патч-тег, см. раздел Security)
- Креды из `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB`
- Наружу пробрасывается `${POSTGRES_HOST_PORT:-15432}` (нестандартный порт,
  чтобы не конфликтовать с локальным PostgreSQL), **только на loopback** —
  `127.0.0.1` и `[::1]`. Порт нужен тестам с хоста; публикация на все
  интерфейсы выставляла бы БД в сеть. Переопределяется через
  `TACITUS_POSTGRES_BIND` вместе с правилом firewall.

  > Публикация на обоих loopback-адресах не избыточна: на Windows `localhost`
  > резолвится сначала в `::1`, и при публикации только на `127.0.0.1` каждое
  > подключение ждёт ~2 с таймаута IPv6 перед откатом на IPv4. Тестовые
  > фикстуры используют `NullPool` — соединение на тест, — поэтому прогон
  > замедлялся почти в десять раз.
- Данные в named volume `postgres-data`
- Healthcheck: `pg_isready`

## Redis

- Образ `redis:7.4.10-alpine`
- Используется как backend `TACITUS_RATE_LIMIT_STORAGE_URI` в production
- Данные в named volume `redis-data`
- Наружу не публикуется

## Nginx

- Порт `80` → внешний (HTTP)
- Порт `443` → внешний (HTTPS, опционально, через Let's Encrypt)
- `/api/` → proxy to `app:8000/` (префикс `/api` срезается, поэтому
  `/api/files/…` попадает в приложение как `/files/…`)
- `/auth/` → proxy to `app:8000/auth/`
- `/health` → proxy to `app:8000/health`
- `/.env` → `deny all` + 404
- `/.well-known/acme-challenge/` → webroot Certbot
- `/` → static React SPA (`/usr/share/nginx/html`)

> Локаций `/hls/` и `/webrtc/` **нет**. Они существовали, но проксировали в
> протоколы, выключенные в `mediamtx.yml` (`hls: no`, `webrtc: no`) в обеих
> конфигурациях — dev и production, — то есть были заведомо нерабочими. При
> этом каждая несла `Access-Control-Allow-Origin *` и собственную копию всех
> security-заголовков (nginx не наследует `add_header` в блок, который
> объявляет свои). Удалены: комплект заголовков теперь в одном месте, а
> production-шаблон Ansible этих локаций и не содержал — дрейф между двумя
> конфигами устранён. Включите HLS/WebRTC в MediaMTX — верните и локации.

> Отдельных location для `/files/` и `/streams/` **нет**: фронтенд ходит к ним
> через `/api/`. Прямой запрос на `http://host/files/...` уйдёт в SPA-fallback.

- Сервис `app` не публикует порт `8000` — приложение достижимо только через
  nginx. На этом основана модель доверенного прокси для `X-Forwarded-For`
  (см. `docs/security.md` → §2.7).

### HTTPS (production)

SSL-сертификаты выпускаются через **Certbot** (Let's Encrypt). Подробнее см. `docs/deployment.md` → раздел «SSL / Let's
Encrypt».

## MinIO

- Внутренний порт `9000` (S3 API)
- Console `9001` (не exposed наружу)
- Bucket `tacitus-files` создаётся init-контейнером

## MediaMTX

- **Образ:** `bluenviron/mediamtx:1.15.1-ffmpeg` (фиксированная версия, не `latest`)
- **Пользователь:** запуск от `1000:1000` (non-root)
- **Порты:** наружу экспонируется только **RTSP `8554/TCP`**, по умолчанию
  на loopback (`TACITUS_MTX_RTSP_BIND=127.0.0.1`)
- **Протоколы:** включён только RTSP (`rtsp: yes`), ретрансляция отключена (`rtmp/hls/webrtc/srt: no`)
- **Аутентификация:** `authInternalUsers` с разделением по действиям —
  `publisher` (publish), `reader` (read/playback), `tacitus-api` (api).
  См. `docs/security.md` §2.8 и ADR-012
- **Запись:** `record: yes`, формат `fmp4`, сегментация по 1 часу
- **Volume:** `./recordings:/recordings` (bind mount на хосте)
- **Конфиг:** `./mediamtx/mediamtx.yml:/mediamtx.yml:ro`, в production
  рендерится Ansible из `mediamtx.yml.j2`
- **Healthcheck:** `nc -z localhost 8554` (проверка доступности RTSP-порта)

## MediaMTX Cleanup

- **Образ:** `tacitus-app:0.1.0` — тот же, что у приложения
- **Назначение:** ротация архивов записей и выгрузка старых сегментов в S3/MinIO
- **Скрипт:** `scripts/mediamtx-archive-manager.py`
- **Зависимости:** `boto3` приходит из сборки образа. Установки пакетов при
  старте контейнера нет: сервис не зависит от доступности PyPI и использует
  тот же SDK, что и приложение
- **Пользователь:** non-root (`tacitus`, uid 1000) — как в образе приложения.
  Каталог записей должен принадлежать `1000:1000`, иначе ротация не сможет
  удалять локальные файлы (ansible создаёт его именно так)
- **Healthcheck:** отключён. Образ приложения объявляет HTTP-проверку порта
  8000, а здесь работает цикл ротации, а не uvicorn
- **Частота:** раз в час (`sleep 3600`)
- **Логика:**
  - удаляет файлы старше `MAX_AGE_DAYS` дней с предварительной выгрузкой в S3
  - если суммарный размер превышает `MAX_SIZE_GB` — удаляет самые старые сегменты до снижения лимита
  - **не видит** файлы, изменявшиеся менее `MIN_IDLE_SECONDS` (300 с) назад, и
    файлы, чьё имя начинается с точки. Первое — открытый сегмент, который
    MediaMTX дописывает каждую секунду; второе — временный файл
    `recording-optimizer`. Выгрузка любого из них означала бы отправку
    полуфайла в S3 и удаление локального оригинала
- **Volume:** `./recordings:/recordings` (общая директория с `mediamtx`)

## Оптимизатор записей

Прореживание статичных кадров: сервис `recording-optimizer` декодирует
закрытые сегменты, выбрасывает кадры, практически не отличающиеся от
предыдущего, и кладёт результат на место оригинала — до того, как его заберёт
архиватор. Обоснование и замеры — ADR-015.

- **Образ:** `bluenviron/mediamtx:1.15.1-ffmpeg` — тот же, что у `mediamtx` и
  симулятора. В нём уже есть ffmpeg 6.1.2 с avfilter (то есть с `mpdecimate`) и
  ffprobe, поэтому сервис не добавляет к стеку ни нового образа, ни второй
  версии ffmpeg. Тащить ffmpeg в `tacitus-app` нельзя: на этом образе работает
  и API, и `mediamtx-cleanup`
- **Entrypoint:** переопределён на `scripts/optimize-recordings.sh` (POSIX
  `sh` — в образе только busybox ash)
- **Выключатель:** `TACITUS_OPT_ENABLED`, по умолчанию `false`. Профиля compose
  здесь нет, в отличие от симулятора: Ansible вызывает compose без
  `--profile`, и сервис за профилем никогда не стартовал бы на сервере.
  Выключенный сервис остаётся живым и молчаливым, а не падает в рестарт-петлю
- **Что делает с сегментом:** `ffmpeg -vf mpdecimate -fps_mode:v vfr
  -c:v libx264 -crf 18 -c:a copy`. Звук не трогается, формат остаётся fmp4,
  выход помечается тегом `tacitus_decimated=1` — по нему сегмент не берётся в
  работу второй раз
- **Таймлиния не меняется:** `-fps_mode vfr` сохраняет исходные PTS выживших
  кадров, поэтому часовая запись остаётся часовой. Видео становится VFR
- **Что защищает оригинал:** результат подменяет запись только пройдя все
  проверки разом — код возврата ffmpeg, наличие кадров, расхождение
  длительности не больше секунды, экономия не меньше
  `TACITUS_OPT_MIN_GAIN_PERCENT`. При любом сомнении временный файл удаляется,
  а оригинал остаётся нетронутым. Возраст файла переносится на результат
  (`touch -r`), иначе архив не уезжал бы в S3 никогда
- **Ожидаемый выигрыш** (замер, 1280x720@25, 60 с): неподвижная сцена и слабый
  шум матрицы — 1500 кадров → 1, до −98 % объёма; сильный шум и непрерывное
  движение — файл **растёт**, и предохранитель по размеру оставляет оригинал.
  Выигрыш определяется шумом матрицы, а не сценой, поэтому пороги
  `TACITUS_OPT_HI` / `_LO` / `_FRAC` вынесены в окружение, а включать сервис
  следует после замера на своей камере
- **Ресурсы:** собственный лимит `2.0` CPU, ffmpeg запускается под `nice`.
  MediaMTX ограничен своим `1.0`, поэтому приём потока оптимизатор не задушит
- **Секреты:** `env_file` нет — сервис не ходит ни в базу, ни в S3
- **Healthcheck:** не объявлен. «Жив ли обработчик» — вопрос к логу (строка
  обхода) и к размеру каталога записей, а не к состоянию процесса, который
  99 % времени спит

## Обрезка записей

Сервис `video-processor` срезает у закрытых сегментов заданную для потока долю
кадра сверху и снизу и кладёт результат на место оригинала. Обоснование —
ADR-016.

- **Перекодирования нет.** H.264 и H.265 несут в SPS «conformance window» —
  прямоугольник, который декодер обязан отрезать при выводе. ffmpeg переписывает
  его битстрим-фильтром (`h264_metadata` / `hevc_metadata`) при `-c copy`, то
  есть работа сводится к ремуксу: секунды на сегмент, нулевая потеря качества,
  размер практически не меняется
- **Это не сокрытие.** Срезанные пиксели остаются в файле и восстанавливаются
  сбросом crop-окна. Механизм убирает лишние зоны кадра (небо, землю, полосу с
  OSD-таймштампом), но не прячет ничего
- **Образ:** собственный, `tacitus-video-processor:0.1.0` из
  `Dockerfile.video-processor`. Не образ приложения: на нём работают API (с
  `read_only`) и ещё два сервиса, которым ffmpeg не нужен. И не образ MediaMTX:
  ffmpeg там есть, но нет ни python, ни моделей, а доли обрезки лежат в таблице
  `streams`. **Это третий ffmpeg в проекте** (Debian-сборка против 6.1.2 в
  образе MediaMTX); при обновлении любого из них см. `docs/upgrades.md`
- **Выключатель:** отдельного нет и не нужен — обрезка включается для каждого
  потока полем `crop_enabled`, по умолчанию выключенным у всех. Поднятый сервис
  без настроенных потоков не трогает ничего
- **Настройки:** читаются напрямую из PostgreSQL на каждом обходе, поэтому
  правка через веб-интерфейс подхватывается к следующему проходу без
  перезапуска. Из секретов сервису передаётся только строка подключения к БД:
  `env_file` нет, ключи S3 и JWT-секрет ему не нужны
- **Арифметика.** Смещения crop-окна абсолютны относительно *кодированного*
  кадра, а не добавляются к отображаемому. Камера 1080p кодирует 1088 строк, 8
  из которых уже срезаны, поэтому «срезать 20 % снизу» — это смещение 216 + 8.
  ffprobe кодированную высоту не сообщает (в сегментах MediaMTX её нет вовсе),
  поэтому паддинг вычисляется из выравнивания по макроблокам и **проверяется**
  по факту, с одной самокорректирующейся повторной попыткой
- **Маркер:** тег контейнера `tacitus_crop=v1:<сверху>:<снизу>:<исходная
  высота>:<паддинг>`. Хранит исходную геометрию, поэтому изменение долей и
  отключение обрезки пересчитываются от неё, хотя исходного файла уже нет.
  Пишется с `-movflags +use_metadata_tags` — без него mp4-муксер выбрасывает
  все нестандартные теги, включая `tacitus_decimated` оптимизатора
- **Что защищает оригинал:** результат подменяет запись только если ffmpeg
  завершился успешно, результат читается и его высота равна расчётной. Возраст
  переносится на результат (`os.utime`), иначе архив не уезжал бы в S3 никогда.
  Временный файл — `.<имя>.tacitus-crop.tmp`: с точки и на `.tmp`, поэтому
  архиватор его не подберёт
- **Порядок относительно архиватора:** обрезка берёт файлы старше
  `MIN_IDLE_SECONDS` (5 минут), архиватор — старше `TACITUS_MTX_MAX_AGE_DAYS`
  (7 суток), поэтому обрезка всегда успевает раньше выгрузки
- **Ресурсы:** лимит `0.5` CPU, ffmpeg под `nice`. Ремукс упирается в диск, а не
  в процессор
- **Healthcheck:** не объявлен, по той же причине, что у оптимизатора

## Симулятор потока

Фальш-камера: публикует в MediaMTX синтетический RTSP-поток, чтобы прогнать
конвейер (публикация → путь MediaMTX → `GET /streams` → запись → архив) без
настоящего оборудования. Инструкция по запуску — в `docs/testing.md`.

- **Образ:** `bluenviron/mediamtx:1.15.1-ffmpeg` — тот же, что у сервиса
  `mediamtx`. В нём уже есть ffmpeg 6.1.2 с libx264 и lavfi, поэтому симулятор
  не добавляет к стеку ни нового образа, ни второй версии ffmpeg
- **Профиль:** `simulator` — единственный профиль compose в проекте. Обычный
  `docker compose up` сервис не поднимает, Ansible вызывает compose без
  `--profile`, а в отрендеренном production-`.env` нет пароля публикатора.
  Это два независимых барьера; третий — проверка в `scripts/healthcheck.sh`,
  которая считает наличие контейнера на сервере ошибкой
- **Entrypoint:** переопределён на `scripts/simulate-stream-entrypoint.sh`
  (POSIX `sh`: в образе есть только busybox ash, ни bash, ни python нет).
  Без переопределения контейнер поднял бы второй RTSP-сервер
- **Режимы:** `continuous` (непрерывная публикация, несколько путей
  одновременно), `reconnect` (цикл публикация/пауза), `negative`
  (одноразовая проверка, что MediaMTX отказывает)
- **Источник:** `testsrc2` + `sine`, кодеки `libx264` и `aac`, две дорожки.
  GOP по умолчанию 1 с: MediaMTX начинает сегмент записи с ключевого кадра, и
  при дефолтном GOP ffmpeg (~10 с) первый файл появлялся бы с задержкой
- **Restart policy:** `no` — упавший симулятор остаётся упавшим и заметным
- **Что НЕ смонтировано:** каталог `./recordings`. Публикатор пишет в сеть, а
  не на диск, и не должен иметь доступа к архиву. Единственный volume — сам
  скрипт, `:ro`; корень контейнера `read_only`, писать можно только в tmpfs
  `/tmp` (туда уходит stderr ffmpeg в негативном режиме)
- **Секреты:** `env_file` нет. Остальные сервисы читают `.env` целиком;
  симулятору достаётся ровно один секрет — пароль учётной записи `publisher`
- **Healthcheck:** не объявлен. «Жив ли симулятор» — вопрос к Control API
  MediaMTX (готов ли путь), а не к контейнеру: `docker ps` показывал бы
  healthy у ffmpeg, пишущего в никуда

## Security

- Версии образов зафиксированы точными патч-тегами, а не только мажорными:
  `postgres:18.6-alpine`, `redis:7.4.10-alpine`, `python:3.14.5-slim`,
  `node:22.23.2-alpine`, `nginx:1.27.5-alpine`, MinIO и MediaMTX — по дате
  релиза. Мажорный тег вроде `18-alpine` не `latest`, но всё равно движется:
  пересборка через полгода принесла бы другой патч-релиз без единого
  изменения в репозитории. Обновление версии — осознанная правка строки;
  проверяется тестом `test_upstream_images_are_pinned_to_an_exact_release`
- MinIO console недоступен извне
- Dev credentials только для локальной разработки
- MediaMTX не открывает порты HLS/WebRTC/RTMP/SRT наружу
- MediaMTX требует аутентификации для publish, read и Control API; анонимный
  дефолт вытеснен явным `authInternalUsers`
- RTSP-порт по умолчанию слушает только loopback
- Порт PostgreSQL публикуется только на loopback (`127.0.0.1` и `[::1]`)
- Записи хранятся в bind-mount `./recordings` с правами non-root пользователя
- Симулятор потока держит действующие учётные данные публикатора, поэтому
  закрыт профилем compose `simulator` и не разворачивается на сервере;
  `scripts/healthcheck.sh` сообщает FAIL, если контейнер всё же найден

# Аудит зависимостей и безопасности

Ручные проверки backend, frontend и образов. Все команды выполняются из корня
репозитория при активированном `.venv` (иначе подставляйте
`.venv/Scripts/python -m …`).

> Зачем это отдельно от тестов. Тесты и линтеры реагируют на изменения кода.
> Уязвимость появляется иначе: репозиторий не менялся, а сегодня опубликовали
> CVE на версию, которая у вас уже запиннена. Поэтому проверки ниже нужно
> запускать по времени, а не по факту правок.

## Когда запускать

| Повод | Что прогнать |
|-------|--------------|
| Перед релизом или деплоем | Всё из этого файла |
| После изменения зависимостей | `pip-audit`, `uv lock --check`, `npm audit` |
| Раз в неделю без всякого повода | `pip-audit`, `npm audit` |
| После смены базовых образов | `docker scout` |

Последняя строка особенно важна: образы закреплены точными патч-тегами
(см. `docs/infrastructure.md` → Security), поэтому автоматических обновлений
безопасности они **не получают**. Это осознанный размен на воспроизводимость,
но следить за выходом патчей теперь нужно вручную.

## Backend

### pip-audit — основная проверка

```bash
pip-audit -r requirements.txt
```

Проверяет ровно то, что попадает в образ: `requirements.txt` — это экспорт
`uv.lock` с хешами, по которому собирается Docker-образ (см. `docs/uv.md`).
Занимает около 40 секунд, требует доступа в сеть.

Полезные варианты:

```bash
pip-audit -r requirements.txt --desc            # с описанием каждой уязвимости
pip-audit -r requirements.txt -f json           # машиночитаемый вывод
pip-audit -l                                    # аудит текущего .venv, включая dev-зависимости
```

**Не используйте `--fix`.** Он перепишет `requirements.txt` напрямую, и файл
разойдётся с `uv.lock`, из которого генерируется. Порядок исправления другой:

```bash
uv lock --upgrade-package <имя>                 # или uv lock --upgrade для всего
uv export --frozen --no-dev --no-emit-project \
  --format requirements-txt --output-file requirements.txt
pip-audit -r requirements.txt                   # убедиться, что ушло
docker compose build app                        # пересобрать образ
```

### Известное состояние

На 2026-09-05 остаётся **одна** уязвимость:

| Пакет | ID | Статус |
|-------|-----|--------|
| `ecdsa` 0.19.2 | PYSEC-2026-1325 | Фикса нет. Принятый риск: приходит транзитивно через `python-jose`, а JWT подписываются HS256 (HMAC), ECDSA-путь не задействован. Обоснование — `docs/security.md` §8.1 |

Если `pip-audit` показывает что-то ещё — это новое, разбирайтесь.

### Согласованность лок-файла

```bash
uv lock --check
```

Отвечает, разошёлся ли `uv.lock` с `pyproject.toml`. Ничего не меняет.

### SBOM

```bash
cyclonedx-py requirements requirements.txt -o sbom.json
```

Состав поставки в формате CycloneDX — для передачи в сканеры или заказчику.
`cyclonedx-py environment` сделает то же по текущему `.venv`, но туда попадут и
dev-зависимости, которых в образе нет.

## Frontend

### npm audit

```bash
cd frontend
npm audit
```

> Состояние на 2026-09-05: **0 уязвимостей**. Найденные в этот день четыре
> (три высокой критичности, в `react-router`, `nanoid` и `postcss`) закрыты —
> подробности в `docs/security.md` §8.1.

Если `npm audit` что-то показал:

```bash
cd frontend
npm audit fix          # правит package.json и package-lock.json
npm ci                 # переустановить строго по обновлённому lock
npm run build          # убедиться, что сборка проходит
```

После этого **обязательно закоммитьте `package-lock.json` вместе с
`package.json`.** Образ собирается через `npm ci`, который отказывается
работать при расхождении этих файлов (см. `docs/frontend.md`). Согласованность
проверяется тестом `test_frontend_lockfile_agrees_with_package_json`.

Если `npm audit fix` предлагает `--force`, не соглашайтесь не глядя: это
мажорные обновления с ломающими изменениями. Такое обновляйте отдельно и с
прогоном сборки.

### Устаревшие пакеты

```bash
cd frontend
npm outdated
```

Колонка `Wanted` — что поставится в рамках текущих ограничений `package.json`,
`Latest` — что вышло вообще. Расхождение `Wanted` и `Current` означает, что
lock отстал от собственных же ограничений.

## Образы

```bash
docker scout quickview tacitus-app:0.1.0
docker scout cves tacitus-app:0.1.0
```

Показывает уязвимости базового образа и системных пакетов — то, что `pip-audit`
не видит: он проверяет пакеты Python, а не `python:3.14.5-slim` под ними.

> Требует `docker login` (учётная запись Docker Hub). Без входа команда только
> предложит авторизоваться.

Проверять стоит все собираемые образы: `tacitus-app:0.1.0` и
`tacitus-nginx:0.1.0`.

## Смежные проверки качества

Не про уязвимости, но входят в тот же ручной прогон перед релизом:

```bash
ruff check app tests
ruff format --check app tests
mypy app tests
pytest tests/ --cov=app --cov-report=term
```

`mypy` и `ruff` запускаются автоматически на каждом коммите через pre-commit,
`pytest` — нет. Перед мержем убедитесь, что в итоговой строке pytest нет
`skipped`: без поднятой PostgreSQL молча пропускается вся логика auth и
репозиториев (`docs/testing.md`).

## Автоматизация

Сейчас всё перечисленное запускается вручную — сознательное решение.

`pip-audit` намеренно **не** включён в pre-commit: он ходит в сеть, добавляет
~40 секунд к каждому коммиту, и его повод сработать — появление нового CVE, а не
изменение кода. Коммит, правящий README, падал бы из-за уязвимости,
опубликованной сегодня утром. Заготовка хука оставлена закомментированной в
`.pre-commit-config.yaml` с этим же пояснением.

Если однажды понадобится автоматизация, подходящее место — запуск по
расписанию (GitHub Actions `on: schedule`, планировщик задач или cron), а не
хук на коммит.
